# CodexのMedium・High運用についてのやり取り

> 保存日時: 2026-09-05 05:26（JST）

## ChatGPT

普段CodexにWikiや学習内容をまとめさせるなら、**Mediumを基準**にするのが一番合うと思う。

OpenAI側も現在、`medium` を品質・信頼性・速度・コストのバランスが取れた出発点として推奨していて、`high / xhigh` は実際に品質向上が必要な難しい仕事に上げる位置づけです。高いreasoningは常に良いわけではなく、過剰探索やoverthinkingで出力品質が落ちる場合もある、と明記されています。

あなたの運用なら、こんな切り分けがよさそうです。

| 推論レベル使いどころ             |                                     |
| ---------------------- | ----------------------------------- |
| **Low**                | 誤字修正、整形、決まった形式への変換、既存ノートの軽い追記       |
| **Medium**             | **普段の学習内容の整理・Wikiへの統合・構成判断**        |
| **High**               | 矛盾が出た箇所、複数ページをまたぐ設計判断、理解が怪しいところの再検証 |
| **xHigh / Extra High** | Wiki全体の監査、難しい仕様調査、設計全体の整合性確認        |

特に今やっている、

```text id="4j3v8a"
GPTで質問
↓
理解する
↓
Codexに会話やメモを整理させる
↓
Wikiへ反映
```

なら、**Medium固定でかなりいい**と思う。

理由は、普段欲しいのが「可能な限り完全な仕様書」ではなく、

```text id="q1c1hy"
今わかったこと
↓
重要な順に整理
↓
既存知識と最低限整合
↓
あとから育てられる形で保存
```

だから。

High以上を常用すると、今回のCSSカスケードみたいに、

```text id="4dn2o3"
「Stylesは基本上から見る」
```

を保存したいだけなのに、

```text id="osvmvp"
origin
importance
layer
encapsulation
scope
specificity
source order
例外……
```

まで一度に整合させようとして、**Codex側の認識解像度が自分の現在の学習解像度を追い越す**可能性が高くなる。

逆にLowだと、既存文章の整形にはいいけど、

> このケースから何を一般化して`01_基礎概念`へ持っていくべきか

みたいな判断では少し弱くなる可能性がある。

なので基準を一言にすると、

```text id="k7y4ux"
Medium = 日常
High = 疑問が出た場所
xHigh = 定期監査
Low = 単純作業
```

でいいと思う。

さらに重要なのは、**Mediumでも「基本・発展・例外の温度差を付ける」というルールはAGENTS側に持たせること**。推論レベルをMediumに下げるだけより、これを組み合わせた方が今のWikiには効く。

たとえばCodexには普段、

```text id="qs6gh2"
学習者が現在使える基本ルールを最優先する。
正確性のための例外で基本説明を弱めない。
例外・仕様上の厳密さは、必要な場合のみ発展へ分離する。
既存の説明に実害のある誤りがなければ、不必要に複雑化しない。
```

くらいを固定して、**Mediumを日常ドライバー**にするのがたぶん一番安定します。

## ChatGPT

MediumとHighの違いは、かなり単純に言うと**どこまで裏で考えに行くか**です。

```text id="fwsz0n"
Medium
→ 普段使い向け
→ 必要な範囲で考える
→ 速度・品質・重さのバランス型

High
→ 難しい判断向け
→ より多くの候補や矛盾を検討する
→ 遅くなりやすいが、難問では強い
```

OpenAIも現在、`medium` を品質・信頼性・速度・コストのバランスが取れた基準点としていて、`high` は複雑な推論やエージェント的な作業で、追加の待ち時間に見合う品質向上がある場合に使う位置づけです。

今のあなたのWiki作業で言うなら、差はこんな感じ。

### Medium

例えば、

> 今日CSSカスケードについて話した内容をWikiにまとめて

と頼むと、

```text id="poua31"
基本ルール
↓
理由
↓
必要な例外
```

くらいで収めやすい。

既存ページとの整合もある程度見るけど、**必要以上に仕様の端まで探索しにくい**。

### High

同じ依頼でも、

```text id="wc6nc5"
この説明は厳密に常に正しいか
↓
仕様ではどう定義されているか
↓
!importantは？
↓
@layerは？
↓
@scopeは？
↓
Shadow DOMは？
↓
継承とは厳密には別処理では？
```

のように、より広い範囲を確認してからまとめようとしやすい。

だから結果として、

**Medium**

> 「Stylesは基本上から見る。理由が必要ならカスケードを見る」

**High**

> 「ただしStylesの縦位置は完全な順位表ではなく、origin、importance、encapsulation context……」

みたいな差が出やすい。

ただ、ここは重要で、**High＝文章が長い設定ではありません**。reasoning effortと出力のverbosityは別です。Highでも「結論だけ出して」と強く指示すれば短くできます。

なので用途で分けるなら、

```text id="bsdw08"
Medium
普段のまとめ
既存ノートへの統合
学習内容の整理
普通のコード修正

High
なぜか辻褄が合わない
設計判断が複数絡む
仕様を確認したい
バグ原因が絞れない
Wikiの内容を監査したい
```

という感じ。

あなたの場合、**Mediumで作る → 違和感が出た箇所だけHighで再検証**がかなり相性いいと思う。

Highを常用すると、能力不足というより逆に、**自分がまだ重要度を判定できない情報まで拾ってくる**ことが負担になりやすい。

## ChatGPT

うん。その目的なら、**普段のCodexはHighを基準にする**のが一番筋が通っていると思う。

Mediumだと「会話を読みやすいノートへ圧縮する」性能としてはかなり使いやすい。ただ、その圧縮の過程で、

```text id="fw9imf"
会話にあった微妙な論点
判断に至った経緯
まだ確定していない違和感
別の概念とのつながり
次に調べる価値のある種
```

まで「本筋ではない」と判断して落とす可能性がある。

それは試験ノートならむしろ長所だけど、今作っているWikiの目的とは少し違う。

今の構想は、

```text id="2iy3d7"
自分
→ 実際に理解・判断する

GPT
→ 対話しながら分解・説明・仮説整理する

Codex
→ 既存Wiki全体を見ながら統合・一般化・矛盾検査する
```

という3者構成だから、CodexまでMediumで強く圧縮すると、3人目を置いている意味が薄くなりやすい。

Highなら多少、

```text id="rle4dd"
「そこまで今いらない」
「これは例外すぎる」
「その厳密さは今の基礎ページには重い」
```

という情報も出してくる。

でも、それを自分で選別する作業そのものが、

**何が基本で、何が例外で、どこまで知れば実務上十分なのか**

を判断する訓練になる。

これはエンジニアになる目的にはかなり重要だと思う。

今回のCSSカスケードもまさにそうで、

```text id="r5k01k"
最初の自分
「DevToolsは上ほど強い」

High Codex
「厳密にはそんな単純ではなく……」

自分
「それは分かった。でも最初に覚えるべき温度は
 『基本上ほど強い』だな」

↓

Wiki
基本：上から見る
理由：カスケード
発展：例外群
```

となった。

この**Highが出した情報を全部採用するのではなく、自分が情報の階層を決め直す工程**に学習効果があります。

なので今の使い分けなら、

```text id="wyy8yp"
Low
→ 機械的な修正・形式変更

Medium
→ 会話の仮まとめ、単純な追記

High
→ 普段のWiki構築の本命

xHigh / Ultra級
→ 難所・定期監査・全体設計の検証
```

くらいが合いそう。

そしてHighで一番重要なのは、**情報量を減らすことではなく、置き場所を制御すること**だと思う。

たとえばCodexに、

```text id="h0v2e1"
重要な例外を発見しても削除しない。
ただし、基本理解を阻害する場合は本文へ混ぜず、
「発展」「注意」「未確認」などへ分離する。

正確さのために基本説明を必要以上に弱めない。

実務上ほぼ遭遇しない仕様上の完全性より、
現在の学習・実装における重要度を優先して構成する。
```

みたいなルールを持たせる。

すると、

**Highの探索能力は残す**

＋

**High特有の「全部同じ温度で出す」問題だけ抑える**

という状態を狙える。

たぶん今後は、推論レベルそのものよりも**Highが拾ってきた情報をどう階層化させるか**の調整のほうが重要になってくる。

最終的には、

> Codexを自分が楽に理解できる性能に落とす

ではなく、

> **Codexは少し自分より先まで見える状態にしておき、自分が採用範囲を決める**

くらいがちょうどいい。

「多少揺らいでも実務につながる性能へ合わせる」という今の目的なら、Highはかなり良い落としどころだと思う。
