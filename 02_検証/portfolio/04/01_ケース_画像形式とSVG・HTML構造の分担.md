# 01_ケース_画像形式とSVG・HTML構造の分担

## このページの扱い

- portfolio 04のLP制作中に出た、Figma素材の書き出し形式、アウトライン文字の扱い、HTMLとSVGの分担、メール画像との違いをまとめる。
- 案件名、固有のロゴ名、素材名は残さず、判断に必要な条件だけを記録する。
- 元のカンプ画像は本文に含まれていないため、個別パーツの正確なHTML構造、SVG化する範囲、`alt` の最終文言は確定しない。
- 一般原理は既存の基礎ノートと照合し、このケースでは制作時の判断順を中心に残す。

## 結論

画像形式は「PNGかSVGか」だけで決めず、元データがベクターかラスターか、Web上で意味や操作を持つかを分けて判断する。

- ロゴ、アイコン、単純な図形、アウトライン化された文字: SVGを優先する。
- 写真: JPEG / WebPを優先する。
- 透過が必要なラスター画像: PNG / WebPを候補にする。
- 見出し、本文、一覧、リンク、ボタン: 可能な範囲でHTMLに意味と操作を残す。
- 単純な背景、線、余白、装飾: CSSを優先する。

LPでも、セクションの意味や操作まで巨大な1枚画像へまとめない。HTMLでページの骨組みを作り、固定された視覚パーツだけをSVGやラスター画像として使う。

## ケース1_素材の性質から画像形式を選ぶ

### 判断表

| 素材 | 優先候補 | 理由 |
|---|---|---|
| ロゴ | SVG | 少ないパスで形を保ち、拡大縮小しても輪郭が崩れにくい |
| アイコン | SVG | 図形として扱いやすく、色や寸法の調整にも向く |
| アウトライン文字 | SVG | パス化された字形を固定して表示できる |
| 写真 | JPEG / WebP | 多数の色と細部を持つラスター画像の圧縮に向く |
| 透過が必要なラスター画像 | PNG / WebP | ピクセル画像の透明部分を保持できる |
| 単純な線・背景・角丸 | CSS | 画像ファイルを増やさず、サイズ変更にも追従させやすい |

### 写真をSVGにしない理由

写真は細かな色の変化を大量のピクセルとして持つ。これを無理にベクター化すると、多数のパスや塗りが必要になり、データ量と描画負荷が増えやすい。

Figmaから写真をSVGとして書き出せても、次の2通りを区別する。

1. 写真を多数のパスへ変換している
   - 複雑なSVGになりやすく、写真向けの圧縮形式より非効率になりやすい。
2. SVG内へラスター画像を埋め込んでいる
   - 写真自体はベクターにならず、拡大耐性や編集性の利点もほとんど得られない。

したがって「写真のSVGは必ず巨大になる」と断定するのではなく、写真にSVGを使っても通常は形式上の利点がなく、JPEG / WebPなどの方が用途に合うと判断する。

## ケース2_アウトライン文字とaltを分けて考える

文字をアウトライン化すると、見た目は文字でも、ブラウザ上では通常の選択・検索・折り返しができるHTMLテキストではなくなる。

そのため、SVG内に意味のある文字が含まれる場合は、見えている文字を機械的にすべて `alt` へ転記するのではなく、その画像が伝える意味と周囲のHTMLを確認する。

### SVG画像だけが見出しを伝える場合

```html
<h2 class="course-heading">
  <img
    src="./img/course-heading.svg"
    alt="仲間と頑張る グループ講習"
    width="320"
    height="80"
  >
</h2>
```

- SVG画像だけが見出しの内容を持つなら、`alt` で同等の意味を伝える。
- `alt` は装飾の形や色をすべて説明する欄ではなく、画像が担う内容・目的を簡潔に置く。

### 同じ内容をHTMLテキストでも置く場合

```html
<h2>仲間と頑張る グループ講習</h2>
<img src="./img/course-heading-decoration.svg" alt="">
```

- HTML側ですでに同じ意味を伝えているなら、装飾SVGは `alt=""` にして重複読み上げを避ける。
- 文字としての修正、折り返し、検索、レスポンシブ対応が必要なら、HTMLテキストを優先する。

## ケース3_ulにするかは見た目ではなく関係で決める

Figma上で複数パーツが一塊に見えても、それだけでは `ul` かどうかは決まらない。

- 同じ種類のコース、特徴、カードなどが反復している: `ul > li` を候補にする。
- 1つの見出し、説明図、装飾のまとまり: 機械的に `ul` にしない。
- 各項目が単独でも読めるカード: `li` の中に `article` を置くことも検討する。
- 読み順や項目の境界が画像なしでは分からない: カンプと文言を確認するまで構造を確定しない。

「どこからどこまでSVGにするか」と「一覧としてどのHTML要素を使うか」は別の判断である。

## ケース4_LPでHTML・SVG・ラスター画像・CSSを分担する

| 担当 | 主に持たせるもの |
|---|---|
| HTML | `header`、`main`、`section`、見出し、文章、一覧、リンク、ボタン |
| SVG | ロゴ、アイコン、アウトライン文字、固定されたベクター図版 |
| JPEG / WebP / PNG | 写真、ピクセル画像、複雑な質感 |
| CSS | 背景色、余白、単純な線、角丸、配置、レスポンシブ調整 |

LPは1ページ内で申し込みや問い合わせへつなげる比重が大きいが、HTML構造が不要になるわけではない。

巨大な1枚SVGを `img` として置くと、通常のHTMLテキストやリンクとしての編集、折り返し、読み上げ、部分的なレスポンシブ変更が難しくなる。セクション単位の構造と操作はHTMLへ残し、その中の固定デザインだけを素材化する。

### LPかどうかだけで画像化範囲を決めない

LPでも、広告流入とデザイン再現を強く優先する場合、検索流入を重視する場合、更新やフォーム操作を重視する場合がある。

そのため、次の2つを分ける。

- 案件仕様で、特定のアウトライン文字や固定デザインをSVGとして使う。
- LPという理由だけで、ページ全体の文章・構造・操作を画像へまとめる。

前者は対象部品の実装条件になり得るが、後者の根拠にはならない。ページの意味、アクセシビリティ、操作、レスポンシブ、更新性、デザイン再現性を確認し、部品単位で画像化の範囲を決める。

```html
<main>
  <section class="course">
    <h2>コース紹介</h2>
    <ul class="course__list">
      <li class="course__item">...</li>
    </ul>
  </section>
</main>
```

## ケース5_メールで画像中心の構成が選ばれる理由

メールはWebページより表示環境ごとの差を受けやすく、複雑なHTML/CSSを組むより、画像へ見た目を固定した方が同じデザインを届けやすい場合がある。

ただし「メールは画像だけでよい」を共通ルールにはしない。

### 画像中心にする利点

- 複雑な装飾やレイアウトを固定しやすい。
- キャンペーン画像全体をリンクとして扱いやすい。
- メールクライアント間の見た目の差を減らしやすい。

### 欠点

- 画像が非表示だと内容が伝わらない。
- 文字の拡大、検索、コピー、読み上げに弱い。
- 小さな文字がスマートフォンで読みにくくなり得る。
- 画像容量が大きいと読み込みへ影響する。

重要な案内や本文はHTMLテキストを優先し、見た目を固定したいキャンペーン部分だけ画像を使うなど、目的に応じて分ける。

## 今回の判断手順

1. Figma上の素材がベクターかラスターかを確認する。
2. そのパーツが内容、操作、装飾のどれを担当するか決める。
3. 見出し・本文・リンク・一覧としてHTMLに残す必要があるか確認する。
4. 同種項目の反復なら `ul > li`、単独のまとまりなら別の構造を検討する。
5. ベクター図形はSVG、写真はJPEG / WebP、透過ラスターはPNG / WebPを候補にする。
6. 画像にしかない意味があれば `alt` で補い、HTMLと重複する装飾画像は `alt=""` にする。
7. PC/SPの表示、画像非表示時、キーボード操作、読み上げ時の情報欠落を確認する。
8. LPという分類だけで決めず、ページの流入経路、検索、更新、操作、デザイン再現性、案件仕様の優先順位を確認する。

## 今回確定しないこと

- 元カンプがないため、質問対象のパーツをどこからどこまでSVGとして書き出すかは確定しない。
- 反復項目の数と関係が見えないため、対象箇所を `ul` にするかは確定しない。
- 周囲のHTMLテキストが分からないため、アウトライン文字の `alt` 文言は確定しない。
- メールの具体的な配信環境・対応要件がないため、画像中心にする範囲は確定しない。
- 案件仕様がアウトラインSVGを求める具体的な対象範囲は、この一般化ケースでは確定しない。
