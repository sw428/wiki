# ケース検証運用

## 目的

- ケース検証は `02_検証` に集約する。
- フォルダは案件ごとに分ける。
- 具体例・事象・検証ログをケースで受け、一般性を確認できた内容だけを `01_基礎` へ戻す。

このファイルは、ケース検証の入口、案件別フォルダの使い方、基礎概念や設計方針への反映先を決めるための共通運用をまとめる。

## 背景

以前は、ケース検証で受けたあとに基礎概念へ戻す流れは作っていたが、基礎概念側と旧実践側の2入口が管理負荷になっていた。

混在ログでは、次の話題が同時に入ることがある。

- 特定ポートフォリオの実装判断
- HTML/CSS/JSなどの基本原理
- BEM命名やSCSS分割のような実務汎用ルール

そのため、ケース検証は `02_検証` に一元化し、案件ごとのフォルダで事象を受けてから、一般化して基礎概念へ戻せるかを判定する。

## 基本ルール

- ポートフォリオ固有の話は、該当案件フォルダへ置く。
- 案件を超えて使える話は、ケース本文内で「一般化できる判断」として残す。
- ケースは案件文脈・検証過程・反映元を残す記録とし、整理済みの一般知識を後から読む正本にはしない。再利用時の参照先は `01_基礎` とする。
- 公式仕様、独立した最小検証、複数の異なるケース、既存基礎概念との一致のいずれかで一般性を確認できた内容だけを `01_基礎` の既存ノートへ統合する。
- 一般性を確認できない判断は、別の管理ファイルへ移さずケース側に残す。
- 短い単語・前提カードが必要な場合だけ `03_参照` へ追加する。
- 判断が割れる場合だけ、ケース本文に理由を短く残す。

## 採用する流れ

1. 貼り付けログを読む
2. まず `02_検証` の案件フォルダで受ける
3. 混在している場合は、必要に応じてケースを分ける
4. ケース本文で、案件固有 / 一般化できる判断 / 実務運用を分ける
5. 根拠と適用範囲を確認し、条件を満たしたものだけ `01_基礎` へ統合する
6. 条件を満たさない判断はケース側に残す

## 細かい運用

`AGENTS.md` では「ケース先行」「案件固有と一般化の切り分け」を判断し、このファイルではケースとして受けたあとの具体的な作業順を扱う。

1. 材料を `新規ケース` / `追記` / `統合` / `保留` に分ける。
2. 実装条件や判断履歴を含む場合は、まずケース側に受ける。
3. 案件固有部分が見えたあとで、再利用できそうな原理をケース本文内で分ける。
4. `01_基礎` に戻す前に、既存ノートと一般性の根拠を確認する。
5. 既存ノートに同じ概念がある場合は、新しい正本を作らず既存ノートへ統合する。
6. 反映後は、ケース末尾から `基礎概念への反映先` へリンクする。
7. 条件、理由、例外、一般化しなかったものが追えるように残す。

## ケース完了前の移項監査

ケース本文の作成とケース一覧への追加だけでは、ケース整理を完了としない。次の監査を同じ作業内で行う。

1. ケース内の論点を、再利用できる最小単位へ分ける。
2. 各論点を、案件固有 / 基礎へ反映 / 既存基礎で充足 / 確認待ちに分ける。
3. 既存基礎との重複は、話題名や結論だけでなく、理由 / 仕組み / 条件 / 例外 / 判断手順まで照合する。
4. 既存基礎に結論があっても、その理由や判断条件が不足していれば、一般性を確認できた不足部分を既存ノートへ統合する。
5. 内容が細かいことを、ケースだけへ残す理由にしない。案件名や素材条件を外して再利用できるなら、粒度に合う既存見出しへ統合する。
6. 新しい設計方針、適用範囲の拡張、ユーザー固有の選択は自動確定せず、確認待ちとしてケースへ残す。
7. 基礎へ反映した場合はケースから反映先へリンクし、既存基礎で充足している場合は重複追記しない。

編集後は、各論点を `基礎へ反映` / `既存基礎で充足` / `ケースのみ` / `確認待ち` のどれにしたかと、反映先または理由を報告する。作業用の判定表をケース本文へ恒久保存すること自体は目的にしない。

## 反映先の判断

### 特定ポートフォリオの話

- 入口: `02_検証/<案件名>`
- 反映先:
  - 案件固有の検証・実装記録 -> `02_検証/<案件名>/...`
  - 一般性をまだ確認できないHTML/CSS/JS原理 -> 元のケースに残す
  - 一般性を確認できたHTML/CSS/JS原理 -> `01_基礎`
  - 自分の採用方針として固定する設計判断 -> `01_基礎/設計` の対象カテゴリ

特定サイトの構造、素材、カンプ、命名、ページ構成に依存する判断は、まず実践ケースとして受ける。
そこから、案件名や素材条件を外しても成立し、一般性の確認材料を持つ原理だけを基礎概念へ戻す。

### 一般的なBEM / SCSSの話

- 入口: `02_検証/<案件名>` または共通運用ケース
- 反映先:
  - 基礎概念として再利用できるCSS原理 -> 必要に応じて `01_基礎/HTML・CSS`
  - BEM命名の採用方針 -> `01_基礎/設計/CSS設計/01_BEMとクラス命名.md`
  - SCSS導入・分割の採用方針 -> `01_基礎/設計/CSS設計/02_SCSSとCSS分割.md`
  - CSS設計全体の採用方針 -> `01_基礎/設計/CSS設計/00_CSS設計整理マップ.md`

BEMやSCSSは、一般概念、案件固有の検証、自分の採用方針が混ざりやすい。
そのため、まずケースで「一般化できる原理なのか、特定案件固有なのか、設計ルールとして固定するのか」を分ける。

### 基礎概念へ戻すもの

- HTML/CSS/JSなど、案件名を外し、一般性の根拠・仕組み・適用範囲・例外まで説明できる基本原理
- 表示ボックス、行ボックス、Flex/Grid、画像比率などの確認順
- BEM/SCSSの話でも、CSSの基本原理として切り出せる部分

### 一般性を確認できるまでケースへ残すもの

- 別の場面でも利用できそうだが、根拠や適用範囲の確認が不足している判断
- 案件固有条件を外したあとに、何が本質的な条件か検証する必要がある内容
- 既存の基礎概念と同じ仕組みか、別の原理かを比較する必要がある内容

### ケース検証へ残すもの

- 特定ポートフォリオの実践判断
- 案件ごとの既存構造、命名方針、素材条件に依存する判断

### 設計方針へ戻すもの

- 自由度が高く、正解が1つに決まりにくい命名・分割・責務境界
- BEMやSCSSの考え方を踏まえた、自分の当面の採用方針
- 案件条件を外しても使いたいが、一般仕様としては言い切りすぎになる運用判断

## 直下に残す例外

- 案件ではなく、このWikiの運用自体を扱うケースだけは、このフォルダ直下に残してよい。

ただし、運用として定着した内容はこのファイルへ統合し、独立ケースとして残し続けない。
