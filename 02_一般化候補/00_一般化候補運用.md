# 一般化候補運用

## このフォルダの役割

`02_一般化候補` は、`03_ケース検証` で得た具体的な観測を、`01_基礎概念` の正本へ戻せる形に整理・検証する中間段階です。

```txt
03_ケース検証
    ↓
02_一般化候補
    ↓
01_基礎概念
```

`04_参照元` はこの成熟段階には含めません。各場所から短く戻るための単語カード・前提カードとして使います。

## ここに置くもの

- ケースから外せる案件固有条件の整理
- 一般化しても残すべき本質的な条件
- 仕組みと理由の説明
- 混同しやすい概念との比較
- 案件に依存しない最小例
- 判断手順、適用範囲、例外
- 一般性の根拠と検証状況
- `01_基礎概念` の反映先候補

確定した基礎概念の本文や、元ケースと同じ長文は置きません。

## Codexの判断余地

この運用は、すべての発見へ同じ工程を強制する固定手順ではなく、案件固有の成功例を誤って普遍化しないためのガードレールです。

次の判断は、禁止事項と自動反映条件の範囲内でCodexが行ってよいものとします。

この裁量は、整理方法、説明形式、既存ノートへの統合方法に適用します。新しい設計方針の採用、既存方針の適用範囲変更、ユーザー固有の判断の一般化には適用しません。

- 誤字や既存説明の改善を、一般化候補へ登録せず既存ノートへ直接反映する
- 既存ノートとの重複が大きい候補を、新規候補にせず参照や説明改善として処理する
- 内容に応じて、表、番号付き手順、最小例、たとえのうち必要な形式だけを選ぶ
- 候補として残すよりケース側に置いた方が判断経緯を追いやすい場合は、無理に抽出しない
- 根拠はあるが新しい方針選択を含む場合は、反映可能まで整理したうえでユーザー確認へ回す

判断項目を満たすこと自体を目的にせず、正本の重複を避け、読み手が条件と理由を追え、次回の判断へ再利用できることを優先します。

## 基礎概念へ進める条件

ケースの表現を抽象的に言い換えただけでは、`01_基礎概念` へ進めません。

元の案件や会話を知らない読み手でも、次を理解できる形に整理できることを条件にします。

1. 何についての知識か
2. なぜその現象や判断が生じるか
3. 別の場面で何を確認すればよいか
4. どの条件では適用できないか
5. 何を根拠に一般化したか

## 外す条件と残す条件

一般化するときは、案件に偶然付随した条件を外します。ただし、結果を変える本質的な条件、仕組み、適用範囲、例外は残します。

| 条件 | 扱い | 例 |
|---|---|---|
| 案件名・サイト名 | 外す | 特定企業のスタッフページ |
| 固有の画像名 | 外す | `hero-staff-sp.jpg` |
| 偶然採用した数値 | 原則外す | 案件固有のブレークポイント |
| 結果を変える条件 | 残す | `min-width` と `max-width` の違い |
| ブラウザや言語の仕組み | 残す | `<picture>` の候補画像選択 |
| 判断するときの順序 | 残す | 標準画像を決めてから条件を指定する |
| 適用範囲・例外 | 残す | 同一画像の解像度違いなら `srcset` も検討する |

案件名を外しただけの判断、理由を説明できない成功例、特定構造でのみ成立する手順は、`03_ケース検証` 側に残します。

## 一般性の確認材料

候補には、次のいずれか1つ以上の確認材料を持たせます。

- 公式仕様または一次情報で確認できる
- 案件から切り離した最小構成で再現できる
- 複数の異なるケースで同じ原理を確認できる
- 既存の基礎概念と同じ仕組みとして説明できる

「複数案件で使えたこと」だけを唯一の条件にはしません。1ケースから得た内容でも、仕様や独立した最小検証で一般性を確認できれば候補を進められます。

## 候補の処理順

1. 元ケースと観測内容を確認する
2. 案件固有の条件を明示する
3. 固有条件を外しても残る条件を確認する
4. 仕組みと理由を説明する
5. 混同しやすい概念と比較する
6. 案件に依存しない最小例へ置き換える
7. 判断手順、適用範囲、例外を整理する
8. 一般性の確認材料を記録する
9. `01_基礎概念` の既存ノートと重複を確認する
10. 昇格・差し戻し・見送りを判断する

## 状態と出口

`02_一般化候補` を恒久的な保留倉庫にはしません。

| 状態 | 意味 |
|---|---|
| 候補 | ケースから抽出した直後 |
| 検証待ち | 一般性の根拠や適用範囲の確認が不足している |
| 反映可能 | `01_基礎概念` へ進める条件を満たした |
| 反映済み | `01_基礎概念` の既存ノートへ統合した |
| 差し戻し | 案件固有だと分かり、`03_ケース検証` へ戻した |
| 見送り | 再利用価値が低い、または候補として維持しない |

`反映可能` は、基礎概念へ進める内容になったことを表し、Codexが自動反映してよいことまでは意味しません。候補一覧の `反映方法` で `自動反映可` または `ユーザー確認` を分けます。

各候補の出口は次のいずれかです。

- 条件を満たしたら `01_基礎概念` の既存ノートへ統合する
- 案件固有だと分かったら `03_ケース検証` へ戻す
- 再利用価値がない場合は見送る

`差し戻し` または `見送り` にした候補は、判断履歴として一覧へ状態と理由を残します。

ファイルや候補記録の削除は、`AGENTS.md` の削除ルールに従い、ユーザーから明示指示がある場合だけ行います。

## Codexが自動反映してよい範囲

自動反映は、次の両方を満たす場合に限ります。

1. 公式仕様、独立した最小検証、または既存原理との一致で内容を確認できる
2. 既存の採用方針・判断範囲を変更しない

両方を満たす場合、次の変更は既存の基礎概念ノートへ事前確認なしで反映してよいものとします。

- 既存ノートに書かれている原理を、別の最小例で明確にする
- 誤記や説明不足を修正する
- 既存の判断範囲を変えず、例や比較表を追加する
- 公式仕様で確認した事実を、既存方針を変えない範囲で補足する

次の場合は、一般性の根拠があっても自動反映しません。反映方法を `ユーザー確認` とし、候補または反映可能の状態で確認を待ちます。

- 新しい設計ルールを作る
- 既存ルールの適用範囲を広げる
- 1つの案件で成功したことだけを根拠にする
- ユーザー固有の好みを一般的な推奨へ変える
- 複数の考え方が成立し、採用判断が分かれる

## 基礎概念へ反映するときの標準順序

基礎概念ノートは、内容に応じて次の順序を基本にします。

1. 結論
2. 何を理解するためのノートか
3. 前提となる仕組み
4. 混同しやすいものとの比較
5. 案件に依存しない最小例
6. 判断するときの順序
7. 適用範囲と例外
8. ケース検証・関連ノート・参照元へのリンク

比較対象がある場合は表、流れが重要な場合は番号付き手順、抽象的で理解しにくい場合はたとえを使います。たとえは理解の補助に限定し、仕様や技術的説明の代わりにはしません。

## フォルダを広げる条件

最初は [一般化候補一覧](./一般化候補一覧.md) の1ファイルで管理します。

`一般化候補一覧.md` には、各候補の元ケース、要点、外した案件固有条件、一般性の確認材料、反映先候補、反映方法、状態と理由を記録します。

`01_基礎概念` へ反映する完成本文を、候補一覧へ重複して保存しません。

1候補の検証内容が長くなり、一覧だけでは条件、理由、例外を追いにくくなった場合に限り、個別候補ファイルへ分けます。

次の状態になったときだけ、分野別ファイルやサブフォルダへの分割を検討します。

- 候補が20〜30件以上になった
- 1候補の検証が長くなった
- HTML・CSS・JavaScriptなど分野別に探しにくくなった
- 複数候補を継続的に並行検証する必要が出た
