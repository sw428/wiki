# カンプ設計とCSS設計で、仕事の認識がずれる理由

カンプ設計とコーディングでは、仕事の起点と、判断を進める方向が異なる。その違いが、それぞれにとって何が当たり前で、どんな説明を相手に求めるかを変える。

このずれを扱うには、各担当工程で判断をどこまで絞れているか、どの情報・技量・規約が不足しているかを照合する。その結果を、実際の判断と成果物へ戻すところまでをフィードバックとして進める。

[画像の高さ設計](../../01_HTML・CSS/12_レスポンシブ画像設計/05_高さで表示領域を作る.md#カンプの切り抜きから高さ固定を実装案にする)でも、同じ基準幅のカンプを比率固定と高さ固定の両方で再現できる。しかし、CSSで両方を作れることと、デザイナーが両方の挙動を意図していることは別である。この区別をつけるには、実装方法の比較に加えて、カンプを作る側と読む側の判断の向きを理解する必要がある。

## 目的から表現へ進む側と、表現から再現方法へ進む側

カンプ設計では、何を見せるか、どの構図を保つか、画面幅が変わったときにどう見せたいかという目的を、具体的な表現へ落とす。目的を踏まえて選択肢を絞り、その結果をカンプに残す。

コーディングでは、渡された表現をブラウザ上で成立させるために、構造・指定・条件を組み立てる。同じ見た目へ到達する実装方法が複数あるため、表現から実現規則の候補を考え、その中から選ぶ。

この受け渡し場面での判断の向きを、ここでは「目的型」と「再現型」と呼ぶ。これは作業の起点を説明する区分であり、人を二種類に固定する分類ではない。

| 観点 | カンプ設計：目的型 | コーディング：再現型 |
| --- | --- | --- |
| 起点 | 何を見せ、どんな状態を成立させたいか | 示された表現をどう成立させるか |
| 判断の向き | 目的から表現を選び、候補を絞る | 表現から複数の実現規則を考え、候補を選ぶ |
| 仕事の中で自明になりやすいもの | この表現を選んだ目的と、その表現の読み方 | 同じ結果を作る方法が複数あることと、実装上の条件 |
| 相手へ求めやすい説明 | なぜ、この表現から意図を読み取らなかったのか | どの根拠で、この実装方法を選ぶのか |

## CSSの選択肢は、カンプの質とは別に生まれる

CSSには、同じ静止状態を複数の規則で作れる性質がある。カンプが丁寧に作られていても、基準幅での再現だけを条件にすると、比率固定と高さ固定のように複数の候補が残り得る。

ここでいうノイズは、「静止状態を作る方法としては成立するが、カンプの設計意図に合うかはまだ分けられていない候補」である。候補が多いこと自体が悪いのではなく、実装可能性と設計意図の判断が混ざると、何を根拠に選ぶかが見えにくくなる。

デザイナーが目的から絞って表現したものに対して、コーダーがCSSの再現可能性から候補を広げ直す。この二つの作業を区別しないと、カンプから意図を読む前に「CSSならどちらでもできる」という状態へ戻ってしまう。

比率固定と高さ固定の例なら、基準幅では同じでも、幅を変えた後の切り抜き方が異なる。デザイナーが伝えようとしているのが後者の挙動なら、基準幅を再現できることだけでは候補を選べない。

## その環境から、それぞれの自己認識と主張が生まれる

デザイナーは、目的を決め、その目的に合わせて表現を選ぶ仕事を繰り返す。その立場では、完成したカンプは単なる寸法の集合ではなく、判断を経て選ばれた表現に見える。自分が使った表現の意味を当然の前提とすると、「このカンプから意図を読めるはず」という認識が生まれやすい。

コーダーは、同じ表現をさまざまな構造や指定で成立させる仕事を繰り返す。その立場では、実装方法の選択と、その方法が成立する条件が重要になる。CSSの構築を判断の起点にすると、「同じ見た目を作れる方法が複数ある以上、どれを選ぶかの根拠が必要」という認識が生まれやすい。

それぞれの認識は、日々の仕事で重視している問いから生まれる。ずれが起きるのは、自分の仕事で自明になっている前提を、相手も同じように共有していると扱ったときである。

## 意図の読解を求めているのに、再現方法の説明が返る

例えば、デザイナーが「このトリミングの仕方から、幅変更時の見せ方を読んでほしい」と話している場面で、コーダーが「この見た目なら高さ固定でも比率固定でも作れる」と返したとする。

デザイナーが問うているのは、カンプの表現をどのような意図として読んだかである。コーダーが答えているのは、その静止状態を何通りの方法で再現できるかである。

この応答は、相手の問いにまだ答えていない。デザイナーには「表現した意図を読んでいない」と映り、コーダーには「選ぶ根拠を説明してもらえていない」と映る。両者が自分の判断の起点だけから話し続けると、互いに何を言いたいのか分からなくなる。

「デザインが分かっていない」「CSSではどちらでもできる」という主張だけを往復しても、どのカンプ情報をどの挙動へ結び付けたかが説明されない限り、候補は収束しない。

## カンプの目的と、CSSを選ぶ根拠をつなぐ

デザイナー側は、どの目的をどの表現へ落としたかに加えて、その表現が実装者にどう読まれるかを考える。自分には自明なトリミングやレイヤー構造でも、複数の読み方が残るなら、表現をそろえるか、挙動を注記する。

コーダー側は、CSSの候補を比較する前に、カンプの寸法・マスク・構図・周囲の配置が何を伝えているかを読む。その読みを、指定されたこと、自分が推定したこと、まだ決まっていないことへ分ける。そこから、意図に整合するCSSを選ぶ。

その際は、一般的なデザイン知識で読めること、現場で共通に決めた表現、未指定の部分を区別する。現場の表現規約が共有されていれば、カンプから挙動を読む根拠になる。一方、作成者だけが知る意味を、読み手にも当然の前提として要求しても伝わらない。

表示高さを保つか比率を保つか、必ず見せる部分はどこか、中間幅でどう変えるか、未指定部分を誰が判断・確認するかを、カンプや共有仕様に残す。実装者はその根拠を使って候補を絞り、幅変更後の表示で確かめる。

## 双方の担当工程で、判断をどこまで絞れているか確かめる

デザイナー側では、レスポンシブ時に何を保ち、何を変えるかが決まっているかを確認する。目的自体が未確定なら、表現規約をそろえる前に、挙動を決める必要がある。目的が決まっているなら、その意図を読み手が必要な範囲まで絞れる表現と規約になっているかを確かめる。

コーダー側では、カンプを観察して意図を読む判断と、その挙動をCSSで実現する判断を分離できているかを確認する。読解の段階に、静止状態だけを再現できるCSS案が混ざっているなら、カンプ情報を根拠に挙動を絞るところへ戻る。

| 担当 | 必要な技量 | 確認する結果 |
| --- | --- | --- |
| デザイナー | 想定する挙動を決め、その意図を表現・注記・規約へ落とす | 何を保ち何を変えるか、どの表現がその根拠かを説明できる |
| コーダー | 状況証拠から挙動を読み、意図の解釈とCSSの候補比較を分ける | 読み取った挙動、支持する情報、残る未確定部分、選んだ実装を説明できる |
| レビュー・管理 | 意図の決定、表現、読解、実装、検証のどこで不一致が生まれたかを照合する | 原因に対応する工程と、修正後に確認する結果を決められる |

規約で絞るのは、必要なレスポンシブ挙動と、その読み方である。同じ挙動を実現できるCSSの書き方まで、常に一通りへ固定する必要はない。

静止カンプや既存の規約から判断できない条件は、追加仕様が必要なものとして扱う。情報がないことと、存在する情報を読み取れないことを区別し、根拠を確認する前に技量不足と決めない。

不足工程の特定、習得中の品質確保、到達条件の置き方は、[カンプ読解と実装判断を身につけるロードマップ](./07_カンプ読解と実装判断を身につけるロードマップ.md)で扱う。

## フィードバックを、ずれが生まれた場所へ返す

デザイナーが高さ固定を想定し、コーダーが比率固定で実装した場合、指示どおり高さ固定へ直すだけでは、異なる結論になった理由が残る。なぜ違う判断になったかを調べ、その原因に対応する情報・技量・規約へ戻す。

確認する順序は、設計意図が決まっていたか、その情報がカンプや規約に表現されていたか、それを読み取れたか、選んだCSSが挙動を実現したか、幅変更後の結果を検証したかである。どこで止まっていたかを、成果物と判断根拠から照合する。

| 確認できたずれ | フィードバックする内容 |
| --- | --- |
| 中間幅の挙動自体が決まっていなかった | 仕様を決める担当と、決定・確認の手順 |
| 意図は決まっていたが、必要な情報がカンプや共有規約に表現されていなかった | デザイン側の表現・注記・規約を作る判断 |
| 必要な情報や共有規約があるのに、読み取らず静止状態の再現だけでCSSを選んだ | 実装側の観察・読解と、候補を選ぶ順序 |
| 意図は読めていたが、選んだCSSがその挙動を実現していない | CSSの設計と実装 |
| 不一致を確認できる表示チェックが行われなかった | 実装後の確認範囲と、完了の基準 |
| 同じ条件で同じ問題が繰り返された | レビューの根拠、担当への返し方、共通基準の更新と再検証 |

この照合には、カンプの情報とCSSの挙動を結び付ける技術的な理解が必要になる。レビューや管理では、両者の主張を聞いたことだけを成果にせず、誰が何を直し、何を見れば解決したと判断できるかを決める。

「経験があれば分かる」に含まれる判断も、観察した情報、そこから読んだ意図、選んだ実装、確認した結果へ分けて残せる。足りない技量が分かったら、その判断を一つずつ習得する方法と、それまで仕事の品質を補う方法を決める。

ここでいう意思疎通は、判断根拠を照合し、各担当の技量・成果物・共通規約へフィードバックし、修正が次の判断と結果へ反映されたかを検証する過程である。フィードバックは、意思疎通が終わった後に別途加えるものとして切り離さない。

会議を開催したこと、意見を言ったこと、相互理解を表明したこと、改善を宣言したことだけでは、この過程が完了したと判断できない。修正した情報と規約を使って、同じ条件から意図した挙動を選び、実装と表示確認へつなげられるかを確かめる。

規約が整うと、必要な情報を渡せているか、読解や実装のどこが不足しているかを確認しやすくなる。技量が上がると、規約の曖昧さや不足も見つけやすくなる。次に同じ状況になったとき、以前より根拠を持って判断できる状態へ更新する。

## この章のまとめ

- カンプ設計は目的から表現を選び、コーディングは表現から複数の実現規則を考える。この起点の違いが、自明と感じることや相手へ求める説明を変える。
- CSSの選択肢の多さと、意図の読解に実装候補が混ざる問題を区別する。
- デザイナーは意図が絞れる表現と規約を作り、コーダーは情報を読んで意図と実装方法を分ける。双方の担当工程で、判断をどこまで収束させられるかを確かめる。
- 不一致の原因を、意図の決定・表現・読解・実装・検証から特定する。追加仕様が必要な条件を、技量不足と混同しない。
- 技量・成果物・規約へフィードバックし、同じ条件で判断と結果が変わったかを検証する。意見交換や改善宣言だけで完了にしない。
