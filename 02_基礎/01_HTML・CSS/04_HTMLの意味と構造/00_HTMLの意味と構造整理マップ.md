## 反映先と確認順

1. 01は人間向け概要とし、見た目・位置・デザインツールの名前ではなく、文書内の担当から要素を選ぶ入口にする。
2. 02〜08はページと記事の範囲、09・10は見出しと操作対象、11〜15は一覧と実装例、16〜19は図版と連絡先の判断へ分ける。
3. 支援技術へ伝わる構造やランドマークの条件は[03の詳細](../../../03_詳細/01_HTML・CSS/02_意味構造とアクセシビリティツリー.md)へ分ける。
4. 文字の画像化とaltは[10](../10_画像と背景/05_文字を画像にする前に確認する.md)、操作範囲・装飾アイコン・埋め込み属性は[15](../15_UI部品の実装判断/00_UI部品の実装判断整理マップ.md)、開閉UIは[JS](../../02_JS/03_UI実装パターン.md#4役で見る最小記憶)、クラス名は[CSS設計](../../07_設計/CSS設計/01_BEMとクラス命名.md#クラスを付ける要素を選ぶ)に分担する。
5. 更新時は、各記事が一つの要素名を説明することではなく、一つの実装判断へ答えているか確認する。別の判断へ広がる説明は対応する記事へ分ける。

## 本文の重複を整理するときの境界

同じ原則が複数の記事へ出てくることだけでは、不要な重複と判定しない。各記事を単独で開いた読者が、その記事固有の判断へ進むために必要な再説明は残す。ただし、共通原則を長く説明し直さず、その要素で何を見るかへ短く接続する。

残すのは、次のいずれかを担う説明とする。

- 記事の主題となる判断軸
- 初めて使うときに起きやすい誤用を防ぐ条件
- 隣接する要素との違いを決める最小限の比較
- 判断軸を直接確認できる最小例
- 本文を単独で読んだときに、結論までつなぐための短い前提

次に当てはまる箇所は、統合または削除の候補とする。

- 01の「見た目ではなく役割で選ぶ」を、記事固有の判断へつなげず説明し直している
- 複数の例が、条件を増やさず同じ結論だけを示している
- 本文で確定した結論を、「判断するときの見方」と「まとめ」で同じ詳しさのまま繰り返している
- 基本の選択に不要な組み合わせを、初心者が最初に読む本文で網羅している
- 別の記事が担当する判断まで、その場で詳しく展開している

細かい内容を機械的に05へ移さない。基本理解後に独立した疑問として読む内容は03、短い定義や確認先は05、別記事の担当なら本文中の必要な位置からリンクする。独立した役割がなければ、移動せず削除する。

削減率や共通テンプレートを先に決めず、記事ごとに「この説明がないと、初心者が何を誤るか」を確認してから整理する。
