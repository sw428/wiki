# 03_カスケード全体の優先順位

記述順と詳細度を確認してもCSSの結果を説明できないときは、カスケード全体の条件へ範囲を広げる。

このページは最初に暗記する一覧ではなく、[DevToolsで適用されたCSSを確認](./01_DevToolsで適用されたCSSを確認する.md)し、[記述順と詳細度](./02_同じ条件の記述順と詳細度.md)だけでは解決しなかったときの確認先である。

## なぜ勝ったかを分けて確認する

次の条件を順に分けて見る。

1. セレクタや条件付き規則が、現在の要素と環境へ適用されるか。
2. CSSの出所と `!important`。
3. Shadow DOMなどのカプセル化コンテキスト。
4. 要素へ直接付いた `style` 属性。
5. `@layer` の順序。
6. セレクタの詳細度。
7. `@scope` がある場合の近さ。
8. それまで同じなら、ソース上の記述順。

実際の問題では、該当する宣言をStylesで見つけ、同じプロパティの打ち消し線とComputedの最終値を確認しながら条件を絞る。

## CSSの出所を区別する

CSSの出所には、主に次の三つがある。

- 作者CSS：Webページ側が指定したCSS。
- ユーザーCSS：閲覧者側が指定したCSS。
- User Agent CSS：ブラウザの標準CSS。

通常指定と `!important` では出所間の優先関係も変わる。「作者CSSなら常にUser Agent CSSより強い」とだけ覚えると、例外を説明できない。

アニメーション、トランジション、Shadow DOMなどが関わる場合は、さらに条件が増える。普段の静的ページで問題になっていない段階から、全順位を暗記する必要はない。

## 継承は直接指定同士の競争ではない

継承は、同じ要素へ直接指定された宣言同士の詳細度競争ではない。継承するプロパティにカスケード値がない場合や、`inherit` が指定された場合などに、親側の値を受け取る。

Stylesの `Inherited from ...` は、この経路を確認する区画として見る。対象要素へ直接指定された値と、親から受け取った値を分けて確認する。

## 「下が土台、上が具体」は設計を読む補助図

次の並びは、CSS設計の積み重ねを理解するためのイメージとして使える。

```text
上  ページ・状態・要素固有の調整
    コンポーネント
    サイト共通
    reset / base
下  ブラウザ標準
```

整理されたCSSでは、DevToolsでもこれに近い見え方になる場合がある。ただし、これはStylesの縦順を保証する規則ではない。CSSは「抽象的か具体的か」という意味を読んで順位を決めていない。実際の勝敗はカスケードの条件で決まる。

CSSファイルをどの責務で分け、どの順に読み込むかという採用方針は、[SCSSとCSS分割](../../07_設計/CSS設計/02_SCSSとCSS分割.md)で扱う。
