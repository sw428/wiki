# なぜ元記事に親コードのせないの？

元の記事：[flex: 1とは？どこがどう伸びるの？](./flex1とは・どこがどう伸びるのか.md)

うん、その考え方なら**逆に `.card` 側のコードは入れない方がいい**。

今回の01記事で本当に見せたいのが、
```css
.body {
  flex: 1;
}
```

で「`.body` の箱そのものが伸びる」という一点なら、親のFlex条件まで同じ記事に書くと、読者の頭がまた広がる。

だから、

> なんで `.body { flex: 1; }` だけで伸びるの？

という疑問は**残していい**。むしろその疑問が出たら、別の01記事へ参照させる。

たとえば、
```text
この記事
↓
.body に flex: 1
↓
「そもそも flex: 1 が効く条件は？」
↓
別記事
「Flexアイテムになる条件」
```

みたいに分ける。

つまり01は、

**一記事で全部説明する**

ではなく、

**今の疑問だけ解く → 次の疑問は別記事へつなぐ**

の方が合う。

今回なら記事内では、
```css
.body {
  flex: 1;
}
```

だけ出して、

> この例では `.body` はFlexの子として扱われている。
> 「なぜFlexの子になるのか」は別記事で確認する。

くらいで止めてもいい。

このやり方の利点は、**読者の頭の中に同時に置く情報を減らせること**。

今回なら頭に残すのは、
```text
flex: 1
↓
bodyという箱が伸びる
```

だけ。

あとで、
```text
なぜ伸びる？
↓
親がFlexだから
```

を別で足す。

さらにそのあと、
```text
縦に伸びるのはなぜ？
↓
flex-direction: column
```

を統合する。

この順番なら、最初から全部を一枚の図に詰め込むより記憶に残しやすい。

だから今の01方針は、

> **前提を全部書かない。今の疑問に必要な情報だけ置く。そこで自然に出る次の疑問は、別の最小理解として参照させる。**

でいい。これはかなり今のWiki設計と噛み合ってる。
