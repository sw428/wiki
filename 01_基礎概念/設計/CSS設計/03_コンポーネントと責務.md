# 03_コンポーネントと責務

## 位置づけ（CSS設計）

このファイルは、コンポーネント本体、配置ラッパー、ページ文脈の責務を分けるための採用方針をまとめるノート。

- 基礎概念: `01_基礎概念`
- 設計: `01_基礎概念/設計/CSS設計`
- 検証元: `02_ケース検証`

## このノートで固定すること

- 共通コンポーネントとして扱う範囲
- `c-` と `p-` の境界
- 親Blockと子Blockの責務分離
- コンポーネント本体と配置ラッパーの分離
- ページ側で上書きしてよいもの / しないもの
- Modifierへ分ける判断
- 再利用へ昇格する判断

## 基本思想

コンポーネントは「見た目と構造の核」を持つ。

一方で、どこに置くか、周囲とどれだけ離すか、何列で並べるかは、使う場所の文脈が決める。

```txt
コンポーネント本体 = 部品としての同一性
配置ラッパー       = 親の中での置き場所
ページ文脈         = 周囲との距離、並び、例外調整
```

## `c-` と `p-` の境界

- 複数ページへそのまま移して使える部品は `c-` にする。
- そのページの構成や文脈に強く依存するものは `p-` にする。
- 判断に迷う段階では `p-` で始め、再利用が明確になった時点で `c-` へ昇格する。

```txt
c-logo / c-button / c-breadcrumb
-> 共通部品として成立する

p-hero / p-staff / p-staff-card
-> そのページ固有のまとまりとして始める
```

例: `p-staff-card` が後からトップページなどでも共通利用されるようになったら、その時点で `c-staff-card` へ昇格する。

## 親Blockと子Blockの責務

- 親Blockは、直下の子要素や子Block同士の配置を決める。
- 子Blockは、自分自身の内部構造と見た目を管理する。
- カード一覧の列数や間隔は一覧側、カード内部の見た目はカード側で扱う。

```css
.staff__list {
  display: grid;
  gap: 40px 20px;
}

.staff-card {
  /* カード内部の配置と見た目 */
}
```

変更時に「どのクラスを触ればよいか」を予測できることを重視する。

## 配置ラッパーと部品本体

親の中で特定の位置に置きたいだけなら、親側のElementで配置を持つ。
部品本体は独立Blockとして残す。

```html
<div class="blog-articles__newsletter">
  <div class="newsletter">
    <div class="newsletter__inner">...</div>
  </div>
</div>
```

- `blog-articles__newsletter`: 親セクション内での置き場所
- `newsletter`: 独立コンポーネント本体

ラッパーを減らしたい場合は、BEMのMixとして1要素に両方のクラスを付ける。

```html
<div class="newsletter blog-articles__newsletter">
  <div class="newsletter__inner">...</div>
</div>
```

このときも、どちらが配置でどちらが部品本体かを説明できる状態にする。

## コンポーネント上書きの境界

### 上書きしてよいもの（ページ側責務）

- `margin`
- `gap`
- `display`（文脈に応じた使い方）
- 位置・周囲余白
- レイアウト都合の並び

### 上書きしないもの（核）

- 形（丸/角など）
- 色の意味（ブランド色・状態色）
- 構造
- `border-radius` など部品固有の骨格

### サイズ差分の扱い

サイズ違いは都度上書きせず、Modifierで吸収する。

```css
.button--sm {}
.button--lg {}
```

## 再利用へ昇格する判断

- 1〜2回だけ出る: ページ固有の `p-` として扱う
- 3回以上出る: 共通コンポーネント化を検討する
- 別ページへそのまま移しても成立する: `c-` へ昇格候補
- 見た目が同じでも意味が違う: 別Blockとして扱う

完全統一ではなく「8割共通、2割ページ調整」が通常運用。

迷ったら次の順で判断する。

1. 核（部品の同一性）なら触らない
2. 配置（文脈差）ならページ側で調整
3. サイズ差はModifierに分離する

## 構造依存セレクタとModifier

一覧内にカードだけが並ぶ前提なら、`:nth-child()` のような構造依存指定で済むことがある。

ただし、広告、見出し、空状態、バナーなどが一覧内に混ざる可能性がある場合は、構造依存セレクタよりModifierを検討する。

```css
.c-blog-card--large {}
```

これは特定Blog実装の正本ではなく、CSS設計側に残す一般判断に限定する。

## まとめ

- 部品の同一性はコンポーネント本体が持つ
- 置き場所と周囲余白は親やページ文脈が持つ
- 再利用が明確になってから `c-` へ昇格する
- 構造依存が不安定になる場合はModifierで意図を明示する
