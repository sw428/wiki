# 00_設計整理マップ

## 目的

このフォルダは、`01_基礎概念` の中で、自分の実装判断として横断的に使う設計方針を置く大カテゴリ。

一般的な仕様説明そのものではなく、検証や基礎概念から得た内容をもとに、自由度の高い設計判断について「自分は当面こう運用する」と固定するために使う。

## 位置づけ

```txt
02_ケース検証
= 具体例、迷った過程、案件条件、検証ログ

01_基礎概念/各分野
= 一般的にはどういう仕組みか、広く通る区別や判断軸

01_基礎概念/設計
= 基礎概念を踏まえて、自分はどう設計判断するか
```

## 現在のカテゴリ

- [CSS設計](./CSS設計/00_CSS設計整理マップ.md)
  - BEM、SCSS分割、レイアウト責務、コンポーネント責務など
- [JavaScript設計](./JavaScript設計/00_JavaScript設計整理マップ.md)
  - 関数設計、モジュール分割、UI状態、イベント責務など
- [WordPress設計](./WordPress設計/00_WordPress設計整理マップ.md)
  - テーマ分割、読み込み責務、静的HTMLからのWordPress化、SCSSとの境界など

## カテゴリの読み方

`JavaScript設計` と `WordPress設計` は、既存の `JS` / `WordPress` ノートを置き換える場所ではない。
まずは設計判断の入口として置き、分野ごとの一般説明や手順は既存カテゴリへリンクする。

設計カテゴリへ置く基準は、単なる分野別知識ではなく、複数ページ・複数案件で再利用する自分の実装判断の正本かどうか。

## 入れるもの

- BEM命名をどの厳しさで使うか
- SCSS分割をどういう責務で分けるか
- `components` / `pages` / `layout` の境界
- 見た目命名ではなく責務命名を優先する方針
- JavaScriptの関数分割、モジュール分割、UI状態管理の判断
- WordPressテーマの分割、読み込み責務、静的HTMLからの変換順
- GPTで初期案を作り、人間が責務で再判定する運用
- 案件ごとに揺れやすいが、自分の中で基準を持ちたい設計判断

## 入れないもの

- 案件固有の条件、素材、納品都合
- 検証中の長い会話ログ
- 一般的な仕様説明だけで済む内容
- まだ採用方針として固めるほどではない思いつき
- 公開記録を増やすためだけのカテゴリやファイル

## 判断の流れ

1. まず `02_ケース検証` で具体例として受ける
2. 案件固有の条件を外しても成立するか見る
3. 一般的な仕組みは `01_基礎概念` の各分野へ戻す
4. 自分の採用方針として使うものだけ、`01_基礎概念/設計` へ置く
5. ルール化した場合も、必要なら後で見直せるように条件と例外を残す

## 書き方

- 「絶対の正解」ではなく「現時点の採用方針」として書く
- 条件、理由、例外をセットで残す
- 一般概念の説明を長く重複させず、必要なら各基礎概念ノートへリンクする
- 案件で起きた経緯は、ケース検証側へ残す
