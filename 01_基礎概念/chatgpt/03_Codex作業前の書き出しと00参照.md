# Codex作業前の書き出しと00参照

## 目的

Codexへ作業を渡す前に、作業範囲と読む場所を絞るためのメモ。

ここでは、いきなり「どのスキルを使うか」から始めるより、依頼内容から領域を決め、そのフォルダの `00_...整理マップ.md` / `00_...運用.md` を読む流れを優先する。

## 基本の流れ

1. 依頼内容を読む
2. どの領域かを決める
3. 対象フォルダの `00_...` を読む
4. 必要な個別ノートだけ読む
5. 作業範囲を書き出す
6. 小さく編集する
7. 差分を確認する

この順にすると、最初から関係ないルールを読みに行く量を減らせる。

## 00参照を優先する理由

- 読む量を減らせる
- 関係ないルールに引っ張られにくい
- 作業範囲を狭くできる
- 変更してよいファイルと、見ればよいファイルを分けやすい
- スキル選択やルール選択のミスを減らせる

このrepoでは、トップの `AGENTS.md` は毎回効かせたい判断を持つ入口として扱う。
細かい読み順やカテゴリ内の判断は、各フォルダの `00_...` に寄せる。

## 作業前の書き出し

書き出しは、長い設計書ではなく、作業範囲を固定する短いメモでよい。

```markdown
## やりたいこと

トップページに新着記事一覧を表示する。

## 触る可能性があるファイル

- front-page.php
- functions.php
- style.css

## 守ること

- 既存HTML構造は大きく変えない
- クラス名は既存のBEMに合わせる
- 投稿ループはWPの関数で扱う

## 変更方針

まず現在のファイルを確認し、新着記事一覧部分だけを変更する。
```

最初にこれを出すと、Codexが広い範囲を勝手に触る事故を減らしやすい。

## コンテキスト容量の考え方

CodexやChatGPTが一度に扱える量には限りがある。

会話内容、開いたファイル、`AGENTS.md`、README、ルール、詳細ノートを全部読ませると、その分だけ作業対象コードを読む余白が減る。

そのため、毎回守る短いルールは `AGENTS.md`、細かい領域ルールは各 `00_...`、長い学習ログは内容ノートへ分ける。

具体的なモデル容量や機能上限は変わりやすいため、数字を暗記せず、必要なときに公式情報で確認する。

## 大規模になったとき

小規模なら、次のように既存フォルダと00系で足りる。

```txt
AGENTS.md
01_基礎概念/
02_実践/
03_参照元/
各フォルダの 00_...
```

大規模になり、1領域の中にさらに判断が増える場合だけ、フォルダ内を分ける。

```txt
wordpress/
  00_WordPress整理マップ.md
  loop.md
  functions.md
  enqueue.md
```

必要なのは `skills` という名前ではなく、領域ごとの入口と、必要な詳細だけ読む構造。

## Codexへの依頼テンプレ

```txt
まず実装しないで、作業計画だけ書いて。
どのファイルを確認するか、どの順番で変更するか、変更リスクも出して。
そのあとこちらがOKしたら実装して。
```

## 判断基準

- 依頼内容からフォルダを決められるか
- そのフォルダの00を読めば足りるか
- いま必要ないルールを読みに行っていないか
- 作業前に、触る可能性があるファイルを絞れているか
- 実装前に、変更方針とリスクを説明できるか

## 一言でいうと

Codexには、全部を最初から読ませるより、内容からフォルダへ飛ばし、そのフォルダの00を読ませる方が安定しやすい。
