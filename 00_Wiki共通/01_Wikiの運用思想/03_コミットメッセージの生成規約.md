# コミットメッセージの生成規約

## この資料の位置づけ

コミットメッセージの生成規約を、Codexの`m`スキルとして登録して使っています。この資料では、その使い方と2026-11-28時点の生成規約を、参考内容として掲載しています。`docs`・`feat`・`fix`などの意味は、下の[typeの分類基準](#typeの分類基準)で確認できます。

実際にCodexが使うスキルはWikiの外に保存しています。このページをWiki内のエージェントや実行用スキルとして登録しているわけではありません。参考資料を掲載するために、実行用のスキルをWiki内へ移す必要もありません。

## 実際の保存場所

著者のWindows環境では、次のフォルダにあります。

```text
C:\Users\user\.agents\skills\m\
└─ SKILL.md
```

実際の生成規約は、この`SKILL.md`に記載しています。この保存場所は著者のPCのものであり、GitHubの読者が直接開くためのリンクではありません。このページだけを編集しても、実行用スキルの内容は変わりません。

## mスキルの使い方

1. 対象のGitリポジトリをCodexで開き、`mスキルを使ってコミットメッセージを作って`と依頼します。スキルを明示して呼び出す場合は、`$m`を入力します。
2. 未ステージ・未追跡の変更があれば、表示された対象を確認し、すべてステージするか、対象を指定するか、ステージしないかを選びます。
3. ステージ済みの差分から生成されたタイトルと本文を確認します。未ステージの変更を対象にするには、先にステージする範囲を承認します。
4. 提示された選択肢から、コミットしてプッシュするか、コミットだけにするか、候補だけ残すかを選びます。承認した範囲の操作は、追加の指示を待たずに実行します。

過去のコミットメッセージを直す場合は、対象範囲を指定して依頼します。旧メッセージと新しい候補を確認してから履歴へ適用し、強制プッシュが必要な場合は、その操作も確認します。

## 自分の環境でも同じ内容を使うには

下に掲載した文章をCodexに渡し、自分の環境へ同じ内容の`m`スキルを登録してもらいます。例えば、次のように依頼できます。

> この資料の「登録に使う内容」にあるname・descriptionと、「生成前の確認」以降の規約本文を使って、ユーザー用のスキルmを登録してください。保存先は私の環境に合わせてください。登録後、対象リポジトリでmスキルを呼び出せるか確認してください。

同じ規約に基づく生成と確認の手順を再現できます。生成される文面は、対象の差分や利用環境によって変わります。`m`はこの環境で使っているスキル名です。別のPCでも使う場合は、その環境にスキルを登録します。

スキルの保存先と呼び出し方法は、[OpenAI公式ドキュメント](https://learn.chatgpt.com/docs/build-skills)でも確認できます。

## 登録に使う内容

`SKILL.md`の先頭には、次の情報を記載します。

```yaml
---
name: m
description: Gitのステージ済み変更からコミットメッセージを生成する
---
```

その後に、以下の「生成前の確認」から末尾までの規約本文を置きます。ここから下は、実行用スキルの本文を参考として掲載したものです。

## 生成前の確認

- 対象リポジトリを確認し、`git status --short --untracked-files=all` でステージ済み・未ステージ・未追跡の状態を確認する。作業ツリーが変更されていることと、その変更がすべてステージ済みであることを区別する。同じファイルにステージ済み・未ステージの両方がある場合も見落とさない。
- 未ステージの変更や未追跡ファイルがあれば、対象のパス・状態・変更の概要を示し、ユーザーから追加指示がなくても「表示した変更をすべてステージする」「対象を指定してステージする」「ステージしない」の選択肢で確認する。確認済みの指示があれば繰り返し尋ねず、その範囲に従う。
- ステージする選択を受けたら、承認されたパスだけをステージする。同じファイルにステージ済み・未ステージの両方がある場合は、残りの変更も含めることを明示する。実行後に状態とステージ済み差分を読み直し、その差分から生成する。無回答を承認とみなさず、無断で `git add` は行わない。
- ステージしない場合は既存のステージ済み差分だけを対象にする。ステージ済み差分がなければ、その旨を伝えて生成を終了する。未ステージの変更や未追跡ファイルを無断で生成対象にしない。
- `git diff --cached --no-ext-diff` などでステージ済み差分全体を確認し、主要な変更を把握する。関係のない本文・画像・履歴の探索や全リポジトリの通読へ広げない。
- メッセージを生成してから、下記の手順でコミット・プッシュを確認する。承認前にコミット・プッシュを実行せず、ステージ操作や履歴の書き換えも自動で行わない。

## 形式と変更の判断

- Conventional Commits 1.0.0 に準拠し、タイトルは `type(scope): 要約` または `type: 要約` とする。scope は対象を明確にできる場合だけ付ける。
- type は下記の「typeの分類基準」から選ぶ。複数のtypeに該当する変更が混在する場合は、変更全体の主目的に基づいて選ぶ。
- 新規ファイルの追加だけを理由に feat にせず、ファイル形式ではなく変更の意味で判断する。学習記事や説明用の図は原則 docs とし、本文に関連してCSSやSVGが変わった場合も、変更全体の主目的を確認する。
- 変更行数の多さだけで重要度を判断せず、変更の意味と対象への影響を考慮する。
- 日本語で書き、識別子や技術用語は必要に応じて原表記を保つ。絵文字は使わない。タイトルの末尾には句点を付けず、本文の文章の末尾には句点「。」を付ける。見出しは句点なしにする。

## typeの分類基準

| type | 意味 | Wiki・公開サイトでの使用例 |
| --- | --- | --- |
| `docs` | 文書の追加・変更 | 記事・説明図・READMEの修正 |
| `feat` | 新機能の追加 | 暗記機能・検索機能の追加 |
| `fix` | 不具合の修正 | 暗記機能の動作不良の修正 |
| `style` | 動作に影響しないコードの整形 | インデント・空白の修正 |
| `refactor` | 動作を変えない内部構造の改善 | JavaScriptの処理の整理 |
| `perf` | パフォーマンスの改善 | ページ表示処理の高速化 |
| `test` | テストの追加・修正 | 動作テストの追加 |
| `build` | ビルド環境の変更 | ビルドツールの設定変更 |
| `ci` | 自動処理環境の変更 | GitHub Actionsの設定変更 |
| `chore` | その他の管理作業 | 管理用ファイルの整理 |
| `revert` | 過去の変更の取り消し | コミットの取り消し |

`feat`と`fix`以外の分類は、プロジェクトごとに運用基準を定められる。この表を本スキルで使う基準とする。仕様の確認先は[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。

## タイトルと本文

- タイトルには主な対象と具体的な変更を示し、「各種修正」「ファイル更新」「整理」だけで終えない。
- タイトルの後に空行を入れ、本文で主要な変更を目的や対象ごとに説明する。何をどう変えたかを書き、理解に必要なら変更前後の違いと関連箇所への影響を示す。
- タイトルは簡潔にし、本文は差分の規模に応じた詳しさにする。行数や項目数を固定せず、重要な変更を省略しない。情報量を増やすためだけの説明、ファイル名の羅列、タイトルの言い換えで埋めない。
- 追加・削除・移動・改名・置換・参照更新を把握し、本文や図の内容変更、配置変更、リンク更新、管理情報の更新を区別する。
- 複数の変更対象や目的がある場合は、必要に応じて見出しで区分する。見出しは意味のまとまりに合わせ、変更内容を減らすために使わない。
- 同じ目的の変更はまとめ、一つの箇条書きに独立した変更を詰め込まず、意味のまとまりで分ける。
- 小規模な変更では見出しを設けず、簡潔に記述する。
- コミットメッセージには、ファイルへのURLや参照用のファイル一覧を自動で付けない。ユーザーが明示的に指定した場合だけ付ける。

## 読みやすさ

- タイトルは簡潔な表現とし、本文は**敬体**で記述する
- 本文は体言止めを多用せず、自然な文章として成立させる
- 対象と変更内容の関係が、読み進めるだけで理解できるようにする
- 文字数の削減を優先して、助詞や必要な説明を省略しない
- 情報を圧縮することよりも、読み手が自然に理解できることを優先する
- 名詞や専門用語を過度に連結しない
- 対象と操作の関係が明確になるように書く
- 一文に複数の変更を詰め込み、理解を難しくしない
- 見出しだけでなく、個々の文章の分かりやすさも重視する
- 作業内容を知らない読者でも変更の概要を追える文章にする
- 正確性を維持したうえで、自然な日本語にする

## 事実と推測

- 対象の差分と、その作業に対応する明示的な情報を根拠にする。理由が確認できなければ創作せず、実施内容を書く。
- 「可読性向上」「保守性改善」などの効果を根拠なく付けない。移動・改名やリンク修正だけを、本文や機能の改善と説明しない。
- 削除対象を根拠なく不要・未使用・重複・旧版と判断しない。作業用・掲載用・採用版・履歴を混同しない。
- テストの追加・修正と実行・成功を区別する。動作確認、公開、採用、承認、同期完了なども、対応する結果や明示情報がある場合だけ記載する。

## 過去のメッセージを書き直す依頼

- ユーザーが指定したコミット範囲だけを対象にし、通常のステージ済み差分とは混ぜない。各コミットの差分と当時の記録を根拠にし、現在の完成状態や後日の修正を過去の実績にしない。
- 判断できないコミットは確認待ちとして分ける。まずコミットID・旧メッセージ・新メッセージの候補一覧を示し、候補の作成だけでは履歴を変更しない。
- 履歴への適用は対象と候補の承認後に行い、復元できる状態を確保する。メッセージ以外のファイル内容・作者情報・履歴構造は変更対象にしない。履歴の書き換えと強制プッシュは別々に承認を得る。
- 候補を提示したら、ユーザーから追加指示がなくても「この候補を指定範囲の履歴に適用する」「候補のまま残す」の選択肢で確認する。適用した場合は照合結果と送信先を示し、強制プッシュが必要なら明示したうえで「プッシュする」「ローカルに残す」を確認する。作業ツリーの未ステージ・未追跡ファイルは過去履歴へ混ぜず、ステージの判断も別に扱う。

## 出力とコミット・プッシュの確認

- 差分と照合し、主要な変更の漏れ、事実と異なる説明、未確認の成果、重複や誇張を取り除く。
- 生成したコミットメッセージを提示する。未ステージ・未追跡の状況通知や、次の承認確認はメッセージ本文へ混ぜず、別に示す。差分がない場合はメッセージを創作しない。
- 対象リポジトリ、現在のブランチ、送信先remote・ブランチ、未プッシュのコミットを確認し、今回送信する範囲をユーザーに示す。送信先が不明なら推測しない。「候補だけ」「コミットしない」「プッシュしない」などの明示的な指示があれば、その範囲を守る。
- メッセージを提示したら、ユーザーがコミット・プッシュに言及していなくても、対象と送信先を示して「このメッセージでコミットしてプッシュする」「コミットだけする」「候補だけ残す」の選択肢で確認する。既存コミットだけを送信する場合は「指定範囲をプッシュする」「プッシュしない」を確認する。先行する未プッシュのコミットも送信対象に含まれる場合は、確認時に明示する。明示的な指示で除外された操作は選択肢に出さず、承認済みの操作は再確認しない。
- ユーザーが「OK」「はい」などで承認したら、確認した範囲のコミット・プッシュを実行する。同じ内容への再確認は挟まない。承認を別の変更、別の送信先、自動ステージ、強制プッシュへ広げない。
- 実行前に対象の差分・HEAD・ブランチ・送信先が確認時から変わっていないか確認する。範囲が変わっていれば差異を示し、元の承認で新しい対象を送信しない。
- 通常のプッシュが拒否された場合は原因と状態を報告し、強制プッシュ、pull、rebase、mergeを勝手に実行しない。成功後はコミットID・送信先・結果を短く報告する。
