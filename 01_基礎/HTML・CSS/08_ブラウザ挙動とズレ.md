# 08_ブラウザ挙動とズレ

## 目的

- 「なぜ画面がずれるか」を、レンダリング工程の因果で説明できるようにする。

## 基本フロー

`HTML解析 → DOM → CSSOM → Render Tree → Layout → Paint → Composite`

- この一連をレンダリングとして扱う。
- [DOM](../../03_参照/DOM.md) と [CSSOM](../../03_参照/CSSOM.md) は、構造とスタイル指定を分けて見るための入口。
- `Layout` は位置とサイズの計算工程。

補足:
- 画面に見える時点では結果がかなり出ている
- ただし内部では、計算順序と依存関係に沿って確定している

## 用語の関係

- Reflow: レイアウト再計算
- Layout Shift: 再計算の結果、表示位置が動く現象
- CLS: Layout Shift の累積指標
- Scroll Anchoring: Shift時に閲覧位置を保とうとするブラウザ補正

## 今回の主因パターン

`レスポンシブ切替 → Layout変更 → Reflow → Layout Shift → Scroll Anchoring補正 → 体感ズレ`

この鎖で起きることが多い。

## 画像が絡む時系列（重要）

画像は非同期ロードなので、次の順になりやすい。

1. 初期 `Layout` / `Paint`
2. JSでスクロール補正
3. 画像ロード完了
4. 画像サイズ確定で再 `Layout` / 再 `Paint`
5. 補正後の位置がまたずれる

つまり「JSが遅い」のではなく、
**JSの後に再レイアウト要因（画像確定）が来る**のが本質。

## スクロール時の見え方

- 単純スクロールは主に再描画（repaint）
- 高さが変わるイベントが混ざると再レイアウト（reflow）も発生
- 画像未予約だと、この再レイアウトが遅れて発火しやすい

## 防止策で何が変わるか

- `width` / `height` 属性: HTML段階で比率予約（最速）
- `aspect-ratio`: CSS適用段階で比率予約（実用上ほぼ同等）
- 予約後は、画像ロード時の高さ変化が減り、JS補正が壊れにくくなる

## 横幅変更が縦ズレを生む理由

- `max-width` や `padding` の変更は横方向の操作でも、テキスト折り返しを変える
- 折り返し行数が増減すると要素高さが変わる
- 結果として section 高さとスクロール位置がズレる

つまり「横幅の変更は直接ではなく、改行を介して縦方向に波及する」。

## CSS側で先に効く3点

1. `width` / `height` または `aspect-ratio` で画像高さを予約する
2. アンカーずれがあるなら `scroll-margin-top` を入れる
3. 画面外描画が重い場合は `content-visibility: auto` と `contain-intrinsic-size` を検討する

```css
main section[id] {
  scroll-margin-top: 80px;
}

main section {
  content-visibility: auto;
  contain-intrinsic-size: 800px;
}
```

補足:
- `content-visibility` は万能ではないため、要素特性やブラウザ差分を見ながら限定適用する。

## カンプのレイヤー寸法をCSSの箱へ直訳しない

デザインツールで表示されるテキストレイヤーの `H` は、背景を含む親要素の高さと同じとは限らない。

CSSへ移すときは次を分けて確認する。

1. `font-size`
2. `line-height`
3. フォントの字面とメトリクス
4. 親要素の `padding`
5. 背景・罫線を持つ要素の実寸

```css
.notice-band {
  font-size: 14px;
  line-height: 1.6;
  padding-block: 3px;
  background-color: #006ea8;
}
```

- テキストレイヤーが21pxでも、背景帯全体が21pxとは限らない。
- まず行の高さと親の内側余白から組み立てる。
- `height` 固定は、部品全体の高さが要件として確定している場合に使う。
- `margin-top: -1px` などの微調整は、通常配置・境界線・端数丸めを確認した後の最終手段にする。

### 選択枠と見えている字形を分ける

デザインツールでテキストレイヤーを選択した時の領域は、レイヤーのバウンディングボックスである。文字や記号として実際に見える線は字形（グリフ）であり、選択枠全体と同じ幅・高さではない。

```txt
テキストレイヤーのバウンディングボックス
┌──────────┐
│    >     │ ← 見えている字形
└──────────┘
```

次の3つを同じものとして扱わない。

| 観測対象 | 分かること |
|---|---|
| デザインツールの選択枠 | レイヤーが持つ範囲 |
| 字形 | 画面上で実際に見える文字の形 |
| ブラウザの要素ボックス | CSSレイアウトで使われる内容・padding・borderを含む箱 |

隣接する文字が別レイヤーなら、まずレイヤー間の距離を測る。1つのテキストレイヤー内に記号と文字が含まれている場合は、オブジェクト間距離として直接測れないため、一時的なレイヤー分割や長方形の重ね合わせで近似する。

フォントが置換されている場合は文字幅やメトリクスも変わる。カンプの数値を仮置きした後、同じ画面幅のブラウザ表示と比較して最終調整する。

## 同じカンプ内でフォントが違って見える時

同じ作品のカンプでも、選択しているテキストレイヤーによってフォント指定が違うことがある。
また、Mac系フォントとWindows系フォントの置換で、同じ文字列でも見た目が変わることがある。

確認する項目は次。

1. `font-family`
2. `font-weight`
3. `font-size`
4. `line-height`
5. 選択しているレイヤーが本当に同じ種類か
6. OSやデザインツール側でフォント置換が起きていないか

たとえば、片方が Meiryo、もう片方が Hiragino 系なら、文字幅・太さ・高さ・余白が変わって見える。

```css
body {
  font-family: "Hiragino Kaku Gothic ProN", "Hiragino Sans", Meiryo, sans-serif;
}
```

この指定は、左から順に使えるフォントを探す。

- Mac: Hiragino系になりやすい
- Windows: Meiryoになりやすい
- どちらもなければ `sans-serif`

つまり、OSごとの自然なゴシック体にはしやすいが、MacとWindowsで完全に同じ見た目にはなりにくい。
カンプに完全に寄せたい場合は、どのフォントを正とするかを先に決める。

`メイリオ` と `Meiryo` は、日本語表示名と英語名の違いとして出ることがある。
CSSでは `Meiryo` を指定すれば通ることが多い。

### 指定フォントとレンダリングフォント

DevToolsでは、CSSで指定・選択されたフォントと、ブラウザが実際の文字描画に使用したフォントを分けて確認する。

- Stylesの `font-family`: CSSに書かれたフォント候補と、その宣言の出所
- Computedの `font-family`: カスケード後に対象要素へ適用されるフォントファミリーの値
- Computed下部の「レンダリング フォント」: Chromeの文字描画で実際に使われたフォント

指定・計算された `font-family` と、実際に描画されたフォント名は同じとは限らない。

```txt
CSSのfont-family
        ↓
カスケード後のfont-familyが決まる
        ↓
ブラウザが利用可能なフォントと収録文字を確認する
        ↓
文字の描画に使うレンダリングフォントが決まる
```

先頭候補が端末にない場合や、そのフォントに対象文字の字形がない場合は、後続候補や別のフォントへフォールバックする。そのため、一つの要素内でも文字によって異なるフォントが使われることがある。

画面内の「左上」「右下」などの位置はDevToolsの配置によって変わるため、位置ではなく `font-family` と「レンダリング フォント」の項目名で探す。

確認先: [Chrome DevTools - Disable local fonts](https://developer.chrome.com/docs/devtools/rendering/apply-effects/#disable-local-fonts)

## 対処順

1. 画像/動画のサイズ予約（`width`/`height`, `aspect-ratio`）
2. 高さが後から変わる要素を減らす（`fit-content` などを点検）
3. それでもズレる箇所に限定して `overflow-anchor: none;`
4. 最後に JS 補正を検討（CSS安定化後）

## 例

```css
.portfolio__list {
  overflow-anchor: none;
}
```

- 乱用せず、問題箇所だけに当てる。

## DevToolsでの見方（Computed / Overlay / Changes）

Stylesでは、確認したいプロパティを探し、上側から有力な宣言をたどる。ただし縦位置だけで勝敗を断定せず、打ち消し線とComputedの最終値を使う。詳細度だけではない優先関係は [CSSカスケードとDevToolsの見方](./15_CSSカスケードとDevToolsの見方.md) で扱う。

### Computedの値

- Computedは「最終採用された結果寄りの値」を見る場所
- 薄い灰色の `height: 439px` などは、CSSに直書きした値ではなく
  レイアウト計算の結果として表示されることがある

### Grid Overlay

- 紫の斜線は `gap` の可視化
- `gap` 数値はその場で直接表示されないことがある
- 空きトラック幅は `Show track sizes` で確認する

### Flexの `space-between`

- Gridのように「この空きが何px」と直接出しにくい
- 実務では `getBoundingClientRect()` で要素間を測る方が速い

### ChangesでDevTools内の編集差分をまとめて見る

ElementsのStylesやSourcesでCSSを試しながら直した場合は、Changesパネルで変更箇所をまとめて確認できる。

- DevTools右上のメニュー → `More tools` → `Changes`
- または `Ctrl + Shift + P` → `Show Changes`

Changesが追跡するのは、DevTools内で行った編集である。CSSはElementsのStylesまたはSources、JavaScriptはSourcesの変更を確認できる。HTMLの追跡はSourcesでLocal Overridesを使った場合が対象になるため、Elementsで一時的に変えたDOMまで常に一覧化されるとは考えない。

ページまたはDevToolsを再読み込みすると、通常の編集差分は消える。再読み込み後も試作を残したい場合はLocal Overrides、ローカルのソースファイル自体へ保存したい場合はWorkspacesを使い分ける。

確認先:

- [Changes: Track your HTML, CSS, and JavaScript changes](https://developer.chrome.com/docs/devtools/changes/)
- [Override web content and HTTP response headers locally](https://developer.chrome.com/docs/devtools/overrides/)

## 回転前の箱と回転後の外接矩形を分ける

`transform: rotate(...)` は、通常のレイアウトで要素の位置とサイズが決まった後の描画へ作用する。回転して見えても、`width` / `height` で作った元のCSSボックス自体が、回転後の横幅・縦幅へ書き換わるわけではない。

たとえば `8.6 × 1px` の細長い長方形を `35.54deg` 回転する。

```css
.diagonal-line {
  width: 8.6px;
  height: 1px;
  transform: rotate(35.54deg);
}
```

| 値 | 意味 |
|---|---|
| `8.6 × 1px` | 回転前のCSSボックス |
| `8.6px` | 回転後も変わらない長辺の長さ |
| 約 `7.58 × 5.81px` | 回転後の図形を水平・垂直の矩形で囲んだ外接範囲 |

幅 `w`、高さ `h` の長方形を第1象限の角度 `θ` で回した場合、軸平行な外接矩形は次で確認できる。

```txt
外接幅 = w × cos(θ) + h × sin(θ)
外接高 = w × sin(θ) + h × cos(θ)
```

細長い要素でも `height: 1px` の厚みがあるため、中心軸の横方向・縦方向の差より、外接矩形は少し大きくなる。

- DevToolsのBox Model: 回転前の `width` / `height` を確認する
- Computedの `matrix(...)`: `rotate()` などを行列へ解決した値が見えることがある
- `getBoundingClientRect()`: transformを反映した軸平行の外接矩形を確認する
- `transform-origin`: 回転の支点と位置を変える。同じ図形・同じ角度なら、外接矩形の幅と高さは変えない

デザインツール側でも、線の始点・終点、strokeを含む選択枠、レイヤーの `W` / `H` を同じ値だと決めつけない。座標差が `7 × 5` の線なら中心軸の長さは `sqrt(7² + 5²) ≒ 8.6` だが、その `7 × 5` が何を表すかはレイヤー種別と測定表示で確認する。

仕様確認先:

- [CSS Transforms Module Level 1 - Transform Rendering Model](https://drafts.csswg.org/css-transforms-1/#transform-rendering)
- [CSSOM View Module - `getBoundingClientRect()`](https://drafts.csswg.org/cssom-view/#dom-element-getboundingclientrect)

## `@media` で「効いていないはずが効く」時の確認順

- 症状:
  - PC用に書いたつもりの `display: flex` がSPでも効く
- 主因:
  - `@media` の `}` が早く閉じて、意図したルールがブロック外へ漏れている
- 確認順:
1. 対象要素を親コンテナで選ぶ（`li` ではなく `ul` など）
2. `Computed` で該当プロパティ（例: `display`）を確認する
3. 値の出どころ（ファイル/行）で `@media` 内外を確認する
4. `Styles` で `}` の閉じ位置を見直す

- 補足:
  - 「要素サイズが 529px だからSP判定」という読み方は誤り。`min-width` 判定は viewport 幅で行われる。

## 新しめ機能の導入判断（CSSネスト / Sass）

- CSSネストはモダン環境で実用化が進んでおり、「ネスト目的だけ」ならネイティブCSSでも運用できる。
- ただし次は別判断が必要。
  - 古め端末を広く含む案件
  - build前提の設計（mixin/関数/分割統合）
  - Sassの `&__element` 連結前提の命名運用

注意点:

- ネイティブCSSネストでは Sass と同じ連結記法（`&__child`）をそのまま使えない。
- 導入判断は「書けるか」ではなく、対象ブラウザ要件と運用要件で決める。

判断順:

1. 対象ブラウザ要件を固定する
2. ネスト以外の機能要件（mixin/分割/連結命名）を洗い出す
3. ネイティブCSSで足りるか、Sass/PostCSSが必要かを決める

## 一言でいうと

画面ズレは、DOM/CSSOMからLayout/Paintへ進む途中で、サイズ・画像・スクロール補正のどこが再計算されたかで見る。
