# 15_CSSカスケードとDevToolsの見方

## 目的

- DevToolsの[Stylesペイン](../../03_参照/ペイン.md)を、最初から詳細度計算へ入らずに読めるようにする。
- 「上ほど強い」という実用上の見方と、CSSが実際に勝敗を決めるカスケードを分ける。
- 1つのCSSファイル内の順番と、HTMLから読み込む複数CSSファイルの順番を同じ原理で捉える。

## このページの読み方

このページは、普段の実装で使う範囲と、問題が起きた時に戻る参照範囲を同じ正本に置いている。

- 普段使う:
  - Stylesではまず上側から有力な宣言を探す
  - 打ち消し線で不採用の宣言を見分け、最終値はComputedで確認する
  - 同じカスケード条件なら後の宣言が勝ち、複数CSSではHTMLの `<link>` 順も関係する
  - 詳細度は `ID - class類 - 要素類` の桁で比較する。`100 / 10 / 1 / 0` は暗算用の入口として使う
- 問題が起きた時に確認する:
  - CSSの出所と `!important` を含む厳密な優先関係
  - Shadow DOMのカプセル化コンテキスト、`@layer`、`@scope`
  - アニメーション、トランジション、`:is()` / `:not()` / `:has()` などを含む例外

後者は存在を知っていればよく、普段から完全な順位や例外を暗記しない。

> [!IMPORTANT]
> まずStylesで有力な宣言を見る → Computedで結果を確認する → おかしい時だけカスケードを分解する。

## 最初に押さえる結論

DevToolsのStylesペインでは、まず次のように見る。

```txt
上側の規則から確認する
打ち消し線がない宣言 = 現在その競合に勝っている候補
打ち消し線 = 現在は採用されていない印。理由は表示から分ける
最終結果だけを見たい = Computedを確認する
```

多くの場合、対象要素へ直接適用される規則は、上側から有力な宣言を探すと早い。
ただし、**Stylesペインの縦位置そのものが、CSSカスケードの完全な順位表なのではない**。

宣言の勝敗には、inline style、`!important`、CSSの出所、カスケードレイヤー、詳細度、スコープ、記述順など、1つのCSSファイル内の詳細度以外の条件も関係する。

そのため、最初は「上側から探す」を入口にし、実際の勝敗は同じプロパティの打ち消し線とComputedで確かめる。Stylesペイン全体を単純に「上のすべてが下のすべてより強い」とは読まない。継承された規則も別の区画に表示される。

## 最初の確認方法

1. Elementsで対象要素を選ぶ
2. Stylesで確認したいプロパティを探す
3. 上側にある、打ち消し線のない宣言と出典ファイルを見る
4. 同じプロパティの打ち消し線、警告アイコン、チェック状態を見て、不採用の理由を分ける
5. 最終的な値はComputedで確認する

### Stylesペインの画面例

![Chrome DevToolsのStylesペインにelement.style、作者CSS、User Agent CSS、継承元が並ぶ画面](./img/DevTools_Stylesペイン.png)

この例では、上から `element.style`、ページ側のCSS、User Agent CSS、継承元の規則が表示されている。User Agent CSSの `margin: 8px` には打ち消し線があり、ページ側の `margin: 0` が採用されている。

上側から有力な宣言を探すと早いが、画面全体の縦位置だけで勝敗を断定しない。同じプロパティの打ち消し線を確認し、必要ならComputedで最終的に使われる値を確認する。

Stylesでは、次の表示を同じ意味にしない。

| 表示                     | 主な意味                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 打ち消し線               | 現在は採用されていない。警告がなければ、まず他の宣言による上書きを疑う                                                   |
| 打ち消し線と警告アイコン | プロパティ名や値が無効、またはブラウザが対応していない可能性がある                                                       |
| チェックが外れた宣言     | DevTools上で一時的に無効化されている                                                                                     |
| 薄い表示と情報アイコン   | 有効なCSSだが、現在の組み合わせでは作用しない場合がある                                                                  |
| `Inherited from ...`     | 親などから継承される規則                                                                                                 |
| Computed                 | カスケードや継承を解決し、Chromeが要素の描画に使う値。プロパティによっては実行時やレイアウト後に解決された値も表示される |

打ち消し線だけでは「詳細度で負けた」とは限らない。理由が必要になった時に、後半のカスケードを確認する。

幅・高さ・余白を図で確認する場合は、[ボックスモデル図で見ている値](./04_ボックスとdisplay.md#devtoolsのボックスモデル図で見ている値) と分けて考える。

## 同じ条件なら後にある宣言が勝つ

カスケード上の他の条件が同じなら、ソース上で後に現れる宣言が勝つ。

```css
p {
  color: red;
}

p {
  color: blue;
}
```

この場合は、後にある `color: blue` が使われる。

これは1つのCSSファイル内だけの話ではない。HTMLから別々に読み込んだスタイルシートは、リンクされた順番に並べたものとして扱われる。

```html
<link rel="stylesheet" href="reset.css" />
<link rel="stylesheet" href="style.css" />
```

同じカスケード条件で競合すれば、後に位置する `style.css` の宣言が勝つ。ネットワーク上でどちらのダウンロードが遅く完了したかは、この順番を決めない。

reset CSSで土台を整え、その後にサイト固有のCSSを適用したい場合は、`reset.css` → `style.css` の順に書く。

## 詳細度の見方

詳細度は、セレクタの種類を左から比較する。最初は次の対応でよい。

| セレクタ                         |  詳細度 | 点数風の覚え方 |
| -------------------------------- | ------: | -------------: |
| `#id`                            | `1-0-0` |            100 |
| `.class`、`[属性]`、`:hover`など | `0-1-0` |             10 |
| `div`、`p`、`::before`など       | `0-0-1` |              1 |
| `*`                              | `0-0-0` |              0 |

`100 / 10 / 1 / 0` は入口用の覚え方であり、本当に点数を足して判定する仕組みではない。実際は `ID - class類 - 要素類` の桁を左から比較する。

そのため、classを多数並べてもIDの桁へ繰り上がるとは考えない。inline styleや `!important` も、この表へ単純に点数追加するものではない。

擬似クラスには例外がある。

- `:where()` 自体と引数は、詳細度が常に `0-0-0`
- `:is()` / `:not()` / `:has()` 自体には擬似クラス1個分を足さず、引数のうち最も高い詳細度を使う

最初から暗記する必要はないが、点数風の計算と結果が合わない時の確認先にする。

## 発展: なぜ勝ったかを確認する

「なぜこの宣言が上書きできないのか」と疑問が出た時だけ、次のカスケード条件を確認する。

1. セレクタや条件付き規則が、現在の要素・環境へ適用されるか
2. CSSの出所と `!important`
3. Shadow DOMなどのカプセル化コンテキスト
4. 要素へ直接付いた `style` 属性
5. `@layer` の順序
6. セレクタの詳細度
7. `@scope` がある場合の近さ
8. それまで同じなら、ソース上の記述順

CSSの出所は、主に次の3つを区別する。

- 作者CSS: Webページ側が指定したCSS
- ユーザーCSS: 閲覧者側が指定したCSS
- User Agent CSS: ブラウザの標準CSS

通常指定と `!important` では出所間の優先関係も変わるため、「作者CSSなら常にUser Agent CSSより強い」とだけ覚えない。

アニメーションやトランジション、Shadow DOMなどが関わる場合は、さらにカスケード上の条件が増える。普段の静的ページで問題になっていない段階から、全順位を暗記する必要はない。

継承は、同じ要素へ直接指定された宣言同士の詳細度競争ではなく、カスケード後のdefaultingで値を決める処理である。継承するプロパティにカスケード値がない場合や `inherit` が指定された場合などに、親側の値を受け取る。Stylesの `Inherited from ...` は、この経路を確認する区画として見る。

## 設計上の「下が土台、上が具体」

次の並びは、DevToolsを最初に読む時とCSS設計を理解するためのイメージとして使える。

```txt
上  ページ・状態・要素固有の調整
    コンポーネント
    サイト共通
    reset / base
下  ブラウザ標準
```

土台の上へ、より局所的な指定を重ねていくイメージである。整理されたCSSでは、DevToolsでもこれに近い見え方になる場合がある。

ただし、これは設計上の積み重ねを理解するための図であり、Stylesペインの縦順を保証する規則ではない。CSSは「抽象的か具体的か」という意味を理解して順位を決めておらず、実際の勝敗はカスケードで決まる。

## 一言でいうと

DevToolsでは、まず上側の有力な宣言、打ち消し線、Computedを見る。理由が必要になった時だけ、出所・`!important`・レイヤー・詳細度・スコープ・記述順へ分解する。

同じ条件なら後勝ちであり、複数CSSの `<link>` 順にも適用される。
