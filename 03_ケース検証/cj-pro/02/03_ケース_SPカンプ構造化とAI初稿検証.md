# 03_ケース_SPカンプ構造化とAI初稿検証

## このページの扱い

- cj-pro `02` のSPカンプを、AIにHTMLの初稿へ変換させてから構造・命名・学習方法を検証した記録。
- 案件名、会社名、住所、人物名、素材名、固有文言は残さず、判断に必要な構造だけを一般化している。
- AIの出力を完成コードとして採用した記録ではなく、誤りや過剰な構造を見つけて直した過程を残す。

## ケース1_SPカンプから大枠だけを読む

### 最初に固定する構造

カンプを見た直後は、寸法や細かいクラス名まで同時に決めず、ページの大枠だけを先に置く。

```html
<body>
  <div class="l-page">
    <header class="header">
      <!-- ロゴ・パンくず -->
    </header>

    <main>
      <div class="mv">
        <!-- メインビジュアル -->
      </div>

      <section class="staff">
        <!-- ページタイトル・説明文 -->
        <!-- スタッフ一覧 -->
        <!-- 一覧リンク -->
      </section>
    </main>

    <footer class="footer">
      <!-- ナビ・連絡先・コピーライト -->
    </footer>
  </div>
</body>
```

この段階で判断するのは、主に次の範囲。

- ページ全体の `header` / `main` / `footer`
- メインビジュアルが章か、単なる表示領域か
- スタッフ紹介が見出しを持つ `section` か
- 繰り返すスタッフ項目を `ul > li` で束ねるか
- 1件分が独立して読める `article` か

画像寸法、余白、レスポンシブ、詳細なBEM名を同じ段階で全部確定しない。

## ケース2_AI初稿のHTMLをそのまま採用しない

AI初稿には、ページ構造を考える材料として使える部分と、文脈を確認して直す部分が混在していた。

| AI初稿で出た形 | 検証後の判断 | 理由 |
|---|---|---|
| ページ上部に `header` | 採用可能 | ロゴやパンくずなど、ページ全体の導入領域として読める |
| セクション内にも `header` | 文法上は可能 | `header` はページ専用ではなく、その範囲の導入・見出し領域にも使える |
| セクション内の見出し群を `div` に変更 | 今回は採用 | `header` を1つに限定するためではなく、見出しと説明をまとめる汎用箱で十分と判断したため |
| 下層ページのロゴを `p` で囲む | 機械的には採用しない | ロゴが `h1` でないことと、ロゴが段落であることは別問題 |
| ページ名を `h1` | 採用 | 下層ページの主題を最上位見出しとして示す |
| スタッフ1件を `article` | 条件付きで採用 | 名前、日付、概要、詳細リンクを持ち、1件で独立して読める場合 |
| リード文にカンプどおりの `br` | 原則見直す | 単なる画面幅による折り返しはCSSと文章幅に任せる。内容上の改行だけ `br` にする |
| `datetime="20XX-03-01"` | 実コードでは不可 | `datetime` には機械可読な有効日付を入れる。仮表記は説明用に限定する |

### 今回の見出し部分

```html
<section class="staff">
  <div class="l-inner">
    <div class="staff__heading">
      <h1 class="staff__title">ページタイトル</h1>
      <p class="staff__description">概要文が入ります。</p>
    </div>

    <!-- スタッフ一覧 -->
  </div>
</section>
```

`staff__heading` を `div` にしたのは、ページ内の `header` を必ず1つにするためではない。今回の内容では、見出しと説明をまとめる配置用の箱として `div` で十分と判断したためである。

## ケース3_下層ページのロゴと `h1` / `p`

下層ページでは、ページ名を `h1` にし、サイトロゴを見出し階層から外す判断は成立する。

ただし、`h1` から外したロゴを自動的に `p` へ置き換えない。

```html
<div class="c-logo">
  <a class="c-logo__link" href="/">
    <img
      class="c-logo__image"
      src="./img/logo.svg"
      alt="サイト名"
      width="199"
      height="25"
    >
  </a>
</div>
```

- ロゴが文章中の段落として扱われるなら `p` も仕様上は使える。
- 単なる配置・グルーピングなら `div` の方が意図を限定しすぎない。
- 親がなくても配置できるなら、リンクを直接置く形も候補になる。
- `p`、`div`、見出しのどれを使うかは、下層ページかどうかだけでなく、その要素の役割から決める。

## ケース4_BEMは名前より所属と独立性を確認する

スタッフ一覧全体と1件分のカードを分ける場合は、次のように判断する。

| デザイン上のまとまり | 役割 | 採用名 | 判断理由 |
|---|---|---|---|
| スタッフ紹介全体 | ページ内の主題を持つセクション | `.staff` | 1つの機能・主題を持つBlock |
| スタッフ一覧 | `staff` 内の反復一覧 | `.staff__list` | `staff` の文脈に所属する |
| 一覧の1項目 | 一覧側の配置単位 | `.staff__item` | 列数や間隔は一覧側が管理する |
| スタッフ1件 | 独立して読めるカード | `.staff-card` | 別の一覧でも扱える単位として分離する |
| 人物画像領域 | カード内のメディア領域 | `.staff-card__media` | `staff-card` の内部要素 |
| 氏名 | カードの見出し | `.staff-card__name` | カードの内容を識別する見出し |
| 補助表示 | カード内の状態・補足 | `.staff-card__badge` | 現時点では独立Blockにする必要がない |

### 一覧・項目・記事を3層で考える

スタッフのインタビュー記事一覧なら、一覧の1項目である `li` の中に、独立した内容である `article` を置く。

```html
<ul class="staff__list">
  <li class="staff__item">
    <article class="staff-card">
      <h2 class="staff-card__name">スタッフ名</h2>
      <time class="staff-card__date" datetime="2026-07-19">
        2026年7月19日
      </time>
      <p class="staff-card__text">インタビューの概要です。</p>
      <a class="staff-card__link" href="./detail.html">続きを読む</a>
    </article>
  </li>
</ul>
```

```txt
ul      = スタッフ全体の一覧
li      = 一覧内の1項目
article = 1件だけ取り出しても意味が通る記事・カード本体
```

`ul` の子として `article` を直接置かず、一覧項目を `li` で表す。名前、日付、概要、詳細リンクがあり、1件だけでも内容が成立する今回は `article` が合う。単なる装飾カードで、独立した記事として読めない場合は `li` 内を `div` にしてよい。

### `article` と画像ラッパーを分けて考える

今回の `article` と `.staff-card__media` は、どちらも内容を囲んでいるが目的が違う。

| 箱 | 目的 | 今回の判断 |
|---|---|---|
| `article.staff-card` | カード1件の意味を表す | 名前、日付、概要、詳細リンクがあり、1件でインタビュー記事として読めるため採用 |
| `div.staff-card__media` | 画像領域の表示を制御する | 円形の枠、比率、切り抜きなどを画像本体と分けて管理する場合に採用 |
| `img.staff-card__image` | 画像データの表示方法を決める | 枠いっぱいに表示する場合は `width`、`height`、`object-fit` を担当 |

```html
<article class="staff-card">
  <div class="staff-card__media">
    <img
      class="staff-card__image"
      src="./img/staff.png"
      alt=""
      width="220"
      height="220"
    >
  </div>

  <div class="staff-card__body">...</div>
</article>
```

`article` はレイアウトのために入れるのではない。また、画像だから必ず `.staff-card__media` で囲むわけでもない。画像へ直接サイズや角丸を指定するだけで足りるなら、次のようにラッパーを省略できる。

```html
<article class="staff-card">
  <img
    class="staff-card__image"
    src="./img/staff.png"
    alt=""
    width="220"
    height="220"
  >

  <div class="staff-card__body">...</div>
</article>
```

カード自体に記事としての独立性がなければ、`article` も必須ではない。`li` や `div` に `.staff-card` を付けて、同じレイアウトを作ることはできる。

名前を暗記するのではなく、次を毎回確認する。

1. そのまとまりは単独で再利用できるか
2. 親Blockがないと意味が成立しないか
3. 一覧の配置と、カード内部の責務が混ざっていないか
4. DOMの深さをそのまま長いクラス名へ写していないか

## ケース5_模写の目的を1回ごとに絞る

毎回ページ全体をフル模写すると、HTMLの意味、BEM、余白、幅、レスポンシブ、画像処理、細かな見た目を同時に扱うことになる。これでは、何を練習しているか判定しにくい。

今回は、次の流れを採用した。

1. 自分でカンプから大枠のタグだけ予想する
2. AIにHTML初稿を作らせる
3. 自分の予想とAI初稿を比較する
4. 今回見る軸を1つに絞る
5. 不自然なタグ、Block分割、命名を直す
6. 「デザイン上のまとまり / 採用名 / 理由」を表にする
7. 重要な一部分だけ、AI初稿を見ずに書き直す
8. 個別判断が固まった後に、フル模写を統合確認として行う

1回の練習対象は、たとえば次のどれか1つでよい。

- HTMLのタグ構造だけ作る
- BEMのBlock分割だけ考える
- スタッフカード1件だけCSSで再現する
- メインビジュアルのレスポンシブ画像だけ検証する

スタッフカードの同型6件を毎回手入力することは、設計判断の練習とは分ける。構造を1件確認した後は、コピー、テンプレート、AI下書きなどで反復部分を作ってよい。

## ケース6_AI下書きを使う時の責任範囲

AIで下書きしてから調整すること自体を問題にしない。確認するのは、完成したコードを自分で扱える状態かどうか。

### 採用できる状態

- カンプと初稿の差を見つけられる
- タグ、見出し階層、BEM分割の理由を説明できる
- 不自然な構造や無効な属性値を修正できる
- 修正後のコードを保守できる
- どこをAIが補い、どこを自分が判断したか区別できる

### 避ける状態

- 出力を理解せずそのまま提出する
- 間違いを検証しない
- なぜその設計になったか説明できない
- 同じ問題が起きた時に修正できない

手書き量だけを学習成果にしない。AI初稿の比較・検証を繰り返し、重要な部分だけ時々何も見ずに再構成して、自分側へ判断が移っているかを確認する。

## ケース7_共通横幅とstaff固有の箱を分ける

PC/SPを通じて複数セクションのコンテンツ幅が共通なら、各Blockへ同じ幅指定を繰り返さず `.l-inner` へまとめる。

```html
<section class="staff">
  <div class="l-inner">
    <div class="staff__body">
      内容
    </div>
  </div>
</section>
```

- `.l-inner`: 共通の最大幅、中央寄せ、左右余白
- `.staff__body`: staff内だけの並びと間隔

`<div class="staff__inner l-inner">` のように同じ要素へ2クラスを付けても、クラスセレクタの詳細度が特別に高くなるわけではない。ただし、両方のクラスが同じ幅や余白を指定し始めると、どちらが担当なのかを追いにくくなる。

今回の採用方針は、役割が別ならHTMLの箱も分けることを基本にする。Block側の箱は、単に内側という意味の `__inner` ではなく、役割に合わせて `__body` や `__content` と命名する。同じ要素へのMixは、責務と対象プロパティが重ならない場合の省略形として扱う。

## ケース8_ボタン型の一覧リンク

スタッフ一覧へ移動するUIは、カンプ上でボタンの形をしていても `a` を使用する。

```html
<div class="staff__more">
  <a class="staff__more-link" href="./staff/">
    スタッフ一覧を見る
    <span aria-hidden="true">→</span>
  </a>
</div>
```

判断基準は見た目ではなく、押した結果。

| 結果 | 採用要素 |
|---|---|
| スタッフ一覧ページへ移動する | `a` |
| 一覧をその場で開閉する | `button type="button"` |
| フォームを送信する | `button type="submit"` |

今回の `.staff__more-link` は「ボタンのような見た目をしたリンク」であり、命名もリンクとして残す。矢印は装飾なので `aria-hidden="true"` とし、読み上げるリンク名は「スタッフ一覧を見る」だけにする。単純な矢印なら、`span` ではなくCSSの疑似要素へ分ける方法もある。

## ケース9_段落の後ろに詳細リンクを置く

カード本文の `p` を閉じた後ろに、詳細ページへの `a` を兄弟要素として置いてよい。

```html
<div class="staff-card__body">
  <p class="staff-card__text">
    インタビューの概要です。
  </p>

  <a class="staff-card__link" href="./staff/detail.html">
    続きを読む
    <span aria-hidden="true">→</span>
  </a>
</div>
```

```txt
staff-card__body
├─ p
└─ a
   └─ span
```

- `p` と `a` は兄弟要素。
- `span` はリンク内の装飾矢印。
- `a` と `span` が既定で行内に流れることは、`a` を `p` 内へ置く必要があるという意味ではない。
- 既定の通常フローでは、`p` がブロックボックスとして終わり、後続の `a` は次の行内レイアウト側に置かれるため、通常は次の行から表示される。
- 次の行になるのは `a` が改行するからではなく、直前の `p` と同じ行ボックスを共有しないため。

リンクをボタン状にするなら、文字だけの場合は `inline-block`、文字と矢印の位置を `gap` や `align-items` で揃える場合は `inline-flex` が候補になる。

## ケース10_このページで `.l-page` が必要か

`.l-page` は「ページだから必ず置く箱」ではない。ページ全体へ次の責務がある時だけ使う。

- サイト全体の最大幅を止める
- ページ全体を中央へ置く
- `body` と別のページ背景を持つ
- ページ全体へ共通する最小高さや表示制御を持つ

今回の会話で確認できた条件は、メインビジュアルを画面幅いっぱいに見せ、本文だけを `.l-inner` で幅制限することだった。ページ全体の最大幅や外側背景は条件に入っていないため、この条件だけなら `.l-page` は不要である。

```html
<body>
  <header class="header">...</header>

  <main>
    <picture class="mv__media">...</picture>

    <section class="staff">
      <div class="l-inner">...</div>
    </section>
  </main>

  <footer class="footer">...</footer>
</body>
```

ただし、同じサイトの既存ページが `.l-page` を共通の外枠として使っている場合は、ページ間の構造を揃えるために残してよい。判断材料はクラス名の有無ではなく、実際に担当させるCSSと既存サイトの構造である。

## ケース11_パンくずは現在地と折り返し単位を分ける

今回の階層は3段階なので、親ページをリンク、最後の現在地を非リンクとして置いた。

```html
<nav class="c-breadcrumb" aria-label="パンくずリスト">
  <ol class="c-breadcrumb__list">
    <li class="c-breadcrumb__item">
      <a class="c-breadcrumb__link" href="/">HOME</a>
    </li>

    <li class="c-breadcrumb__item">
      <a class="c-breadcrumb__link" href="/section/">親ページ</a>
    </li>

    <li class="c-breadcrumb__item" aria-current="page">
      現在のページ
    </li>
  </ol>
</nav>
```

- `nav`: 現在地をたどるナビゲーション領域
- `ol`: 上位から現在地へ進む順序
- 親ページ: 移動できる `a`
- 最後の項目: 現在地。`aria-current="page"` を付けるならここだけ
- 区切り記号: 階層そのものではなく視覚的な補助

区切りを2個目以降にだけ出す場合は、隣接兄弟セレクタと疑似要素を組み合わせられる。

```css
.c-breadcrumb__list {
  display: flex;
  flex-wrap: wrap;
}

.c-breadcrumb__item {
  display: flex;
  white-space: nowrap;
}

.c-breadcrumb__item + .c-breadcrumb__item::before {
  margin-inline: 6px;
  content: ">";
}
```

`flex-wrap` は一覧を項目単位で次の行へ送れるようにし、`white-space: nowrap` は1項目の文字列が途中で割れるのを防ぐ。`align-items: center` は必須ではなく、区切りと文字のサイズや高さが違って上下にずれる時に追加する。

`content: ">"` は簡単な視覚実装だが、読み上げ環境によって装飾記号がノイズになる可能性は残る。階層の意味を記号だけに頼らず、必要なら支援技術でも確認し、CSSの線・背景による記号か `aria-hidden="true"` の実要素へ切り替える。

## ケース12_疑似要素の位置をベースラインの終点で説明しない

`::before` は、対象要素の内容の先頭にCSSが生成するボックスである。

```txt
開始タグ
→ ::before
→ 元からある子要素・テキスト
→ ::after
→ 終了タグ
```

`::before` が左端に見える理由を「1語目のベースラインの終わりから描画される」とは説明しない。生成される順序と、その要素が参加するレイアウト文脈を分けて考える。

- 通常の行内配置では、ソース上の改行やインデントも空白処理の対象になる。
- `white-space: normal` と `nowrap` は連続する空白を折り畳む。`nowrap` の追加役割は自動折り返しを止めること。
- 親をFlexコンテナにすると、疑似要素と子要素はflex itemとして並び、空白だけのテキスト列は独立したflex itemとして描画されない。
- FlexにしてもDOM上の改行文字が削除されるわけではない。
- 必要な距離はソースコードの改行に任せず、`gap` または疑似要素の `margin` で指定する。

文字が2行目で左へ戻って見えたのは、文字の描画領域内で折り返した行が、その領域の行頭から始まったためである。パンくずでは、文字列の途中へ改行を入れず、一覧側だけを項目単位で折り返す方が扱いやすい。

## ケース13_カンプの選択枠と字形を分けて測る

デザインツールで文字レイヤーを選択した時の青い領域は、文字レイヤーのバウンディングボックスである。記号や文字として実際に見える線は字形（グリフ）であり、両者は同じ寸法ではない。

```txt
テキストレイヤーの選択枠
┌──────────┐
│    >     │ ← 見えている字形
└──────────┘
```

選択枠には、テキストボックスの幅・高さ、行の高さ、フォントメトリクスなどが関係する。そのため、選択枠の幅をそのまま「記号の見える幅」やCSSの `margin` へ直訳しない。

測定は次の順で行う。

1. 文字が別レイヤーなら、隣のレイヤーとの距離を測る。
2. 1つのテキストレイヤーなら、必要に応じて一時的に分割するか、長方形を重ねて見える距離を確認する。
3. 使用フォントが一致しない場合は、カンプ値を仮置きにして、ブラウザ上で同じ画面幅へ合わせて微調整する。
4. バウンディングボックス、字形、ブラウザの要素ボックスのどれを比べているかを言葉にする。

## ケース14_左30pxと全幅画像の責務を分ける

余白を `margin` と `padding` のどちらにするかは、「全体レイアウトかどうか」だけでは決めない。空白が箱の境界の内側か、別要素との外側距離かを見る。

今回のヘッダーは、ロゴが中央、パンくずだけが左端から30px離れている。30pxがヘッダー内の全要素に共通する安全余白ではなく、パンくずだけの配置距離なら、配置用の箱へ外側余白を持たせる。

```css
.header__breadcrumb {
  margin-inline-start: 30px;
}
```

他のヘッダー要素も同じ左端へ揃える場合は、共通親の内側余白へ切り替える。

```css
.header__inner {
  padding-inline: 30px;
}
```

パンくずの右に残る広い空間は、短い内容を引いた残りであり、カンプ上の見た目だけを根拠に固定の `margin-right` として入れない。

メインビジュアルは画面幅いっぱいにするため、`.l-inner` の外へ置く。SPは枠比率、PCは高さ500px固定という今回の条件をCSSへ分ける。

```html
<main>
  <picture class="mv__media">
    <source
      media="(min-width: 768px)"
      srcset="./img/mv-pc.jpg"
      width="1920"
      height="500"
    >
    <img
      class="mv__image"
      src="./img/mv-sp.jpg"
      alt=""
      width="375"
      height="400"
    >
  </picture>

  <section class="staff">
    <div class="l-inner">...</div>
  </section>
</main>
```

```css
.mv__media {
  display: block;
  width: 100%;
  aspect-ratio: 375 / 400;
  overflow: hidden;
}

.mv__image {
  display: block;
  width: 100%;
  height: 100%;
  object-fit: cover;
}

@media (min-width: 768px) {
  .mv__media {
    height: 500px;
    aspect-ratio: auto;
  }
}
```

この条件では、PCカンプの幅をそのまま固定 `width` にしたり、固定高さと重複する `aspect-ratio` を追加したりしない。画像と後続見出しの距離は、画像内部ではなく、後続セクションまたは配置文脈で管理する。

## ケース15_円形画像は外周・内側の画像枠・画像データを分ける

今回の人物画像は、カンプ上の外周が `210px` の円で、その内側に `10px` 分の背景色が見える構成だった。外周と内側の画像枠を同じ寸法として扱わない。

```txt
外側の円              210 × 210
  └─ padding 10px
      └─ 内側の画像枠 190 × 190
          └─ 元画像の表示範囲
```

```css
.c-staff-card__media {
  width: 210px;
  aspect-ratio: 1;
  padding: 10px;
  border-radius: 50%;
  background-color: var(--color-circle);
  box-sizing: border-box;
}

.c-staff-card__frame {
  width: 100%;
  height: 100%;
  overflow: hidden;
  border-radius: 50%;
}

.c-staff-card__image {
  display: block;
  width: 100%;
  height: 100%;
  object-fit: cover;
  object-position: center;
  transform: scale(1.1);
}
```

- `.c-staff-card__media`: 外周 `210px` と背景色のリングを担当する。
- `.c-staff-card__frame`: `190px` の内側で、拡大した画像を円形に切り抜く。
- `.c-staff-card__image`: 元画像をどの位置・倍率で見せるかを担当する。

`box-sizing: border-box` によって、`210px` の中に左右のpaddingも含まれる。今回の全称セレクタにも同じ指定はあるが、これがない `content-box` の状態では、`width: 210px` に左右 `10px` ずつが加わり、外周は `230px` になる。

外周がカンプと合っているのに人物の大きさだけが違う場合は、外側の `width` や `padding` を動かさない。見える位置だけなら `object-position`、さらに拡大したいなら、切り抜き枠を固定したまま画像側の `transform: scale(...)` を調整する。

`scale()` はレイアウト上の外周寸法を変えず、描画結果を拡大する。今回は `.c-staff-card__frame` の `overflow: hidden` が、内側の円からはみ出した描画を切り取る。

## ケース16_カンプの `315 × 84` を直指定値と決めつけない

SP幅 `375px` で `.l-inner` の左右に `30px` の余白がある場合、通常フローのブロックである説明文の使用幅は、ほかの指定がなければ次の関係から `315px` になる。

```txt
375 - 30 - 30 = 315
```

これは `.staff__description { width: 315px; }` を指定したからではなく、包含ブロック内の利用可能幅から `width: auto` の使用値が決まった結果である。

同様に、単純なテキストが4行あり、各行の `line-height` が `21px` なら、paddingやborderがない説明文の内容高はおおむね次の結果になる。

```txt
4行 × 21px = 84px
```

```css
.type-13-regular-21 {
  font-size: 13px;
  line-height: 21px;
}
```

`line-height: 1.6` なら計算値は `20.8px` なので、4行は `83.2px` 相当になる。カンプの `21px` が意図した行高として確認できている場合は `21px` を使えるが、選択枠が `84px` だったという理由だけで親へ `height: 84px` を固定しない。

今回のHTMLのように `<br>` で4行を固定するなら、`white-space: nowrap` があっても `<br>` の強制改行は残る。ただし、画面幅に応じて自然に折り返す本文なら、`white-space: nowrap` とカンプ由来の `<br>` は外し、中間幅で行数と高さを確認する。

## ケース17_回転した1px線の長さと外接矩形を分ける

今回の斜線は、太さのない数学上の線ではなく、`8.6 × 1px` の細長い長方形をCSSで回転したものだった。

```css
.staff__more-link::after {
  width: 8.6px;
  height: 1px;
  transform: rotate(35.54deg);
  transform-origin: right center;
}
```

DevToolsで確認できる値は、同じ寸法を別表示したものではない。

| 観測する値 | 今回の値 | 意味 |
|---|---:|---|
| 回転前のCSSボックス | `8.6 × 1px` | `width` / `height` で作った長方形 |
| 長辺の長さ | `8.6px` | 回転しても変わらない長方形の長辺 |
| 回転後の軸平行な外接矩形 | 約 `7.58 × 5.81px` | 斜めの長方形全体を水平・垂直の矩形で囲んだ範囲 |

幅 `w`、高さ `h` の長方形を角度 `θ` だけ回した時、第1象限の角度では外接矩形を次で確認できる。

```txt
外接幅 = w × cos(θ) + h × sin(θ)
外接高 = w × sin(θ) + h × cos(θ)
```

今回の `w = 8.6`、`h = 1`、`θ = 35.54°` を入れると、約 `7.58 × 5.81px` になる。1pxの厚みも外接幅・外接高へ加わるため、中心軸の横方向・縦方向の差だけを測った値より大きく見える。

カンプ側の `7 × 5` が線の始点と終点の座標差を示している場合、線の中心軸の長さは次のように約 `8.6px` になる。

```txt
sqrt(7² + 5²) ≒ 8.6
```

ただし、デザインツールの `W` / `H` が常に始点・終点の差を表すとは限らない。線レイヤー、選択枠、strokeの端のどれを測っているかは先に確認する。

ブラウザは `rotate()` を変換行列として扱うため、Computedに `matrix(...)` が出ることがある。`transform-origin` は回転の支点と描画位置を変えるが、同じ長方形を同じ角度で回すだけなら外接矩形の幅・高さは変えない。

単純な装飾線ならCSSの疑似要素でよい。始点・終点の座標、線端、矢印形状をデザインデータと明示的に対応させたい場合は、SVGの `line` / `path` も候補にする。

## ケース18_背景画像リンクの固定幅と親の配分を分ける

フッター内で、文字リンクを画像の上に置き、リンク面全体を押せるようにする。
背景画像が装飾で、リンクの意味をHTMLの文字で伝えられる場合は、`a` 自身を面にして `background-image` を置ける。

```html
<ul class="footer-links">
  <li class="footer-links__item">
    <a class="footer-links__link" href="#">
      リンク
    </a>
  </li>
  <li class="footer-links__item">
    <a class="footer-links__link" href="#">
      リンク
    </a>
  </li>
</ul>
```

```css
.footer-links {
  display: grid;
  grid-template-columns: repeat(2, 112px);
  justify-content: center;
  gap: 16px;
}

.footer-links__link {
  display: grid;
  place-items: center;
  width: 100%;
  min-height: 48px;
  box-sizing: border-box;
  background: url("../img/link-bg.jpg") center / cover no-repeat;
}
```

今回のリンク群は共通のインナー幅いっぱいへ伸ばす部品ではなく、インナー内に置く小さな固定サイズの部品として読んだ。そのため、親Gridに固定列幅を持たせて中央へ配置する。

```css
/* 固定サイズの部品を2個並べる */
grid-template-columns: repeat(2, 112px);

/* 親の利用可能幅を2列へ配り直す */
grid-template-columns: repeat(2, minmax(0, 1fr));
```

`repeat(2, ...)` は同じ列定義を2回繰り返すだけで、列を可変にはしない。可変かどうかは、中へ置く `112px` と `1fr` の違いで決まる。

ここでの「親が責務を持つ」は、必ず `1fr` にするという意味ではない。

- 親: 固定列か可変列か、列数、間隔、グループ全体の配置を決める。
- 子: 与えられたセルをリンク面として使い、自分の文字と背景を配置する。
- `width: 100%`: 子がセルを埋める必要がある場合の指定であり、親子分離そのものの必須条件ではない。

この見方は、親が枠を作り、子画像が `width: 100%; height: 100%` で従う `aspect-ratio` のケースと表面上は似ている。ただし仕組みは別で、Gridの `fr` は利用可能な横幅の配分、`aspect-ratio` は一方の寸法からもう一方を計算する。

親へ幅の判断を集めるとレスポンシブ変更箇所は追いやすくなるが、固定列を指定しただけで自動的に全画面幅へ対応するわけではない。固定列の合計と `gap` が対応する最小画面幅へ収まらない場合は、メディアクエリ、`minmax()`、`clamp()` などで別途切り替える。

背景画像自体にリンク名などの意味があり、HTMLの文字だけでは内容を伝えられない場合は、装飾背景として扱わず `<img>` と代替テキストを使う。

## ケース19_auto marginを親の余りとして読む

スタッフカード内の画像枠を中央へ置く時、`margin-inline: auto` はページ全体ではなく、画像枠を含むカードの利用可能幅を基準にする。

```css
.c-staff-card {
  width: 277px;
}

.c-staff-card__media {
  width: 210px;
  margin-inline: auto;
}
```

この構造では、カード幅 `277px` から画像枠 `210px` を引いた `67px` が余りになる。左右のauto marginへ `33.5px` ずつ配られるため、画像枠がカード内で中央に置かれる。

親と子が同じ幅なら余りはなく、`margin-inline: auto` が計算されても見た目は動かない。DevToolsでは対象だけでなく、親の幅と左右に配れる余りを一緒に見る。

短い見出しやラベルは、`width: fit-content` で内容に近い幅へ縮めてから `margin-inline: auto` を使うと意図を表しやすい。一方、長い説明文は折り返し位置も設計対象になるため、`max-width` で行長を決める方が扱いやすい場合がある。

## ケース20_DevTools内の試作変更をChangesで確認する

Stylesで余白や幅を何度も試した後は、ChangesパネルでDevTools内の変更をまとめて確認する。

- DevTools右上のメニュー → `More tools` → `Changes`
- または `Ctrl + Shift + P` → `Show Changes`

ChangesはDevToolsで行った編集の確認用であり、元のCSSファイルへ自動保存する機能ではない。ページまたはDevToolsを再読み込みすると通常の差分は消えるため、採用する値は再読み込み前にソースへ戻す。

再読み込み後も試作を残すならLocal Overrides、ローカルのソースへ直接保存するならWorkspacesを検討する。HTMLは、Elementsで一時的に変えたDOMが常にChangesへ並ぶわけではなく、SourcesでLocal Overridesを使った変更が追跡対象になる。

## ケース21_3枚の固定カードが成立する幅からブレークポイントを決める

PCカンプの幅が `1600px` でも、ブレークポイントを `1600px` やその割合から決めるわけではない。今回のPC配置で維持したいカード3枚、`gap`、左右余白が収まる最小幅から判断する。

カードが1枚 `277px` なら、3枚だけで `831px` 必要になる。

```txt
277px × 3枚 = 831px
```

共通インナーの左右paddingが各 `30px` の場合、viewportが `864px` では内容幅が約 `804px` しかなく、カード3枚の合計だけでも入らない。`gap` を考える前に不足するため、固定幅の3列PC配置を `864px` から始めるのは成立しない。

viewportが `1024px` なら内容幅は約 `964px` になり、カード3枚を引いた残りは `133px` になる。2つの `gap` と追加余白の合計がこの範囲へ収まるなら、`1024px` をPC側の開始点にできる。

```txt
1024px - 左右padding 60px - カード合計 831px = 133px
```

今回は中間レイアウトを作らず、SPと3列PCの2段階にするなら、`@media (min-width: 1024px)` の1本へ整理する方針は妥当。ただし、採用前に `1023px`、`1024px`、カンプ幅までの中間値で、カード、`gap`、文字の折り返しが崩れないか確認する。
