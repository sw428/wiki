# ケース検証運用

## 目的

- ケース検証は `03_ケース検証` に集約する。
- フォルダは案件ごとに分ける。
- ケースから抽出した一般化候補は `02_一般化候補` で確認し、条件を満たしたものだけを基礎概念へ戻す。

このファイルは、ケース検証の入口、案件別フォルダの使い方、一般化候補や設計方針への反映先を決めるための共通運用をまとめる。

## 背景

以前は、ケース検証で受けたあとに基礎概念へ戻す流れは作っていたが、基礎概念側と旧実践側の2入口が管理負荷になっていた。

混在ログでは、次の話題が同時に入ることがある。

- 特定ポートフォリオの実装判断
- HTML/CSS/JSなどの基本原理
- BEM命名やSCSS分割のような実務汎用ルール

そのため、ケース検証は `03_ケース検証` に一元化し、案件ごとのフォルダで受けてから、一般化候補として扱うかを判定する。

## 基本ルール

- ポートフォリオ固有の話は、該当案件フォルダへ置く。
- 案件を超えて使える話は、ケース本文内で「一般化できる判断」として残す。
- 一般化できそうな判断は、`02_一般化候補/一般化候補一覧.md` へ登録する。
- `02_一般化候補/00_一般化候補運用.md` の確認条件を満たしたものだけを `01_基礎概念` の既存ノートへ統合する。
- 短い単語・前提カードが必要な場合だけ `04_参照元` へ追加する。
- 判断が割れる場合だけ、ケース本文に理由を短く残す。

## 採用する流れ

1. 貼り付けログを読む
2. まず `03_ケース検証` の案件フォルダで受ける
3. 混在している場合は、必要に応じてケースを分ける
4. ケース本文で、案件固有 / 一般化候補 / 実務運用を分ける
5. 一般化候補があれば `02_一般化候補` へ登録する
6. 根拠と適用範囲を確認し、条件を満たしたものだけ `01_基礎概念` へ統合する

## 細かい運用

`AGENTS.md` では「ケース先行」「案件固有と一般化の切り分け」を判断し、このファイルではケースとして受けたあとの具体的な作業順を扱う。

1. 材料を `新規ケース` / `追記` / `統合` / `保留` に分ける。
2. 実装条件や判断履歴を含む場合は、まずケース側に受ける。
3. 案件固有部分が見えたあとで、再利用できそうな原理を候補として抽出する。
4. 候補を `02_一般化候補/一般化候補一覧.md` へ登録し、ケース末尾に候補IDを残す。
5. `01_基礎概念` に戻す前に、既存ノートと一般性の根拠を確認する。
6. 既存ノートに同じ概念がある場合は、新しい正本を作らず既存ノートへ統合する。
7. 反映後は、ケース末尾と候補一覧に `基礎概念への反映先` を記録する。
8. 条件、理由、例外、一般化しなかったものが追えるように残す。

編集後は、何を `03_ケース検証` に残し、何を `02_一般化候補` へ登録し、何を `01_基礎概念` / `04_参照元` へ反映したかを報告する。

## 反映先の判断

### 特定ポートフォリオの話

- 入口: `03_ケース検証/<案件名>`
- 反映先:
  - 案件固有の検証・実装記録 -> `03_ケース検証/<案件名>/...`
  - 抽象化できそうなHTML/CSS/JS原理 -> `02_一般化候補`
  - 一般性を確認できたHTML/CSS/JS原理 -> `01_基礎概念`
  - 自分の採用方針として固定する設計判断 -> `01_基礎概念/設計` の対象カテゴリ

特定サイトの構造、素材、カンプ、命名、ページ構成に依存する判断は、まず実践ケースとして受ける。
そこから、案件名や素材条件を外しても成立しそうな原理を一般化候補へ送り、確認条件を満たしたものだけを基礎概念へ戻す。

### 一般的なBEM / SCSSの話

- 入口: `03_ケース検証/<案件名>` または共通運用ケース
- 反映先:
  - 基礎概念として再利用できるCSS原理 -> 必要に応じて `01_基礎概念/HTML・CSS`
  - BEM命名の採用方針 -> `01_基礎概念/設計/CSS設計/01_BEMとクラス命名.md`
  - SCSS導入・分割の採用方針 -> `01_基礎概念/設計/CSS設計/02_SCSSとCSS分割.md`
  - CSS設計全体の採用方針 -> `01_基礎概念/設計/CSS設計/00_CSS設計整理マップ.md`

BEMやSCSSは、一般概念、案件固有の検証、自分の採用方針が混ざりやすい。
そのため、基礎概念へ直接入れず、まずケースで「一般化候補なのか、特定案件固有なのか、設計ルールとして固定するのか」を分ける。

### 基礎概念へ戻すもの

- HTML/CSS/JSなど、案件名を外し、一般性の根拠・仕組み・適用範囲・例外まで説明できる基本原理
- 表示ボックス、行ボックス、Flex/Grid、画像比率などの確認順
- BEM/SCSSの話でも、CSSの基本原理として切り出せる部分

### 一般化候補へ送るもの

- 別の場面でも利用できそうだが、根拠や適用範囲の確認が不足している判断
- 案件固有条件を外したあとに、何が本質的な条件か検証する必要がある内容
- 既存の基礎概念と同じ仕組みか、別の原理かを比較する必要がある内容

### ケース検証へ残すもの

- 特定ポートフォリオの実践判断
- 案件ごとの既存構造、命名方針、素材条件に依存する判断

### 設計方針へ戻すもの

- 自由度が高く、正解が1つに決まりにくい命名・分割・責務境界
- BEMやSCSSの考え方を踏まえた、自分の当面の採用方針
- 案件条件を外しても使いたいが、一般仕様としては言い切りすぎになる運用判断

## 直下に残す例外

- 案件ではなく、このWikiの運用自体を扱うケースだけは、このフォルダ直下に残してよい。

ただし、運用として定着した内容はこのファイルへ統合し、独立ケースとして残し続けない。
